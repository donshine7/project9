# 의견제출통지서·거절결정서 자동 다운로드 기획

작성: 2026-09-18, 갱신: 2026-09-21. 상태: **우선순위 1과 2 구현 및 검증 완료, 우선순위 3의 OA 수동 단건 실행 경로 구현 완료, 거절결정 확장 기획 완료**. P261252 1차 OA를 실제 다운로드·검증·ZIP 생성·intake 게시했으며 거절결정 실제 게시와 예약 실행은 아직 활성화하지 않았다.

세 문서 종류의 Outlook 자동 감지, 장진태 직접 수신 조건과 단계별 자동 게시 활성화는 [Outlook 통지 메일 자동 다운로드 트리거 기획](./OUTLOOK_NOTICE_AUTO_TRIGGER_PLAN.md)을 따른다.

## 1. 목표와 확정 범위

Outlook의 `국내특허 OA/ 우선심사 보완` 폴더에서 의견제출통지서(OA) 또는 거절결정서 접수를 감지하고, EasyPAT의 **동일 통지 건에 연결된 통지서·인용문헌·첨부 전체**를 ZIP 한 개로 묶는다. 업무요청 메일과 담당자 지정 메일은 각각 근거로 보존하되 같은 통지 건을 중복 다운로드하지 않는다.

저장 위치:

```text
C:\Users\donsh\OneDrive\Desktop\ONEDRIVE\Desktop\[상상] 업무분류\0-0. intake\
```

파일명:

```text
[당소관리번호 전체] nOA (YYYY-MM-DD)(YYYY-MM-DD).zip
[당소관리번호 전체] 거절결정 (n차)(YYYY-MM-DD)(YYYY-MM-DD).zip
```

거절결정의 첫 괄호는 해당 사건의 거절결정 차수이며, 뒤의 두 날짜는 통지일과 확인된 마감기일이다. 사용자 답변으로 거절결정 별도 표기와 관련 첨부 전체 포함을 확정했다. 날짜 형식은 이 기획안의 제안이다. 사건번호는 출원번호가 아닌 당소관리번호이며 모든 접미사를 보존한다.

폴더에 함께 들어오는 일반 보정요구·우선심사결정·등록결정은 이번 다운로드 대상에 포함하지 않는다. `우선심사신청보완요구서`는 [별도 자동 다운로드 기획](./PRIORITY_EXAM_SUPPLEMENT_DOWNLOAD_PLAN.md)에 따라 독립 통지 종류로 처리한다. OA 대응 초안 송부·독촉·제출완료 메일만으로 새 통지 건을 만들지 않는다.

## 3. 처리 흐름

```text
지정 Outlook 폴더 읽기
  → 메일 원본 중복 제거
  → 접수 후보 추출 및 전체 당소관리번호 대조
  → EasyPAT 사건·진행기록 조회
  → 동일 통지 건 식별 및 두 메일 연결
  → 통지 종류·통지일·기일·종류별 차수 검증
  → 해당 통지 건의 첨부 전체 목록 확정
  → 로컬 임시 다운로드·파일 검증
  → ZIP 검증
  → intake에 덮어쓰기 없이 게시
  → 다운로드 이력·근거·완료 상태 기록
```

1. Outlook 저장소와 폴더 식별자를 설정에 고정한다. 표시명에는 `/`가 있지만 내부 경로에는 `%2F`가 있으므로 경로 문자열을 임의 분할하지 않는다. 본 자동화는 지정 폴더만 대상으로 하며 기존 전체 메일 갱신기의 폴더 범위를 변경하지 않는다.
2. 기존 읽기 전용 COM 수집 방식을 재사용한다. 메일 이동·삭제·읽음 변경·회신은 하지 않는다.
3. 제목과 본문의 OurRef를 추출한다. 제목·본문 충돌, 여러 사건 표기, 새 번호 형식은 확인 대기로 둔다. 회사명·메일 제목 전체를 식별자로 사용하지 않는다.
4. 두 메일이 모두 올 때까지 기다릴 필요는 없다. 먼저 온 한 통과 EasyPAT 근거로 통지 건을 확정할 수 있으면 처리하고, 나중 메일은 기존 통지 건에 연결한다. 담당자 지정 메일의 `OA`만으로 새 접수를 확정하지 않는다.
5. 전체 당소관리번호와 출원번호를 대조하고 해당 접수 통지 행을 선택한다. 수신시각은 조회 범위를 좁히는 보조 근거이며 같은 날 수신되었다는 사실만으로 병합하지 않는다.
6. 필수 메타데이터 또는 첨부가 없으면 ZIP을 만들지 않고 이유를 남긴다. 대상 첨부가 모두 검증된 경우에만 완료한다.

## 4. 중복 방지: 메일과 통지 건을 별도로 관리

| 계층 | 식별·판정 | 동작 |
|---|---|---|
| 같은 메일 재수집 | Message-ID 우선, 없으면 저장소/EntryID와 정규화 내용 해시로 보완 | 메일 원본 재저장 방지 |
| 서로 다른 두 안내메일 | 검증된 동일 통지 건에 여러 mail_item 연결 | ZIP 1개, 근거 메일 2개 |
| 같은 사건의 다음 OA | 통지 식별값·통지일·종류를 대조 | 이전 OA와 별도 패키지 |
| 동일 실행의 재시작·동시 실행 | 통지 건+첨부 버전의 유일 제약, 작업 잠금, 완료 이력 | 중복 다운로드·파일 생성 방지 |

**권장 통지 키:** 전체 당소관리번호 + 통지 종류 + 검증된 외부 통지 식별값. EasyPAT `sequence`는 식별값 후보이며 OA 차수가 아니다. 실제 필드 의미와 안정성을 확인한 뒤 키로 채택한다. 외부 식별값이 없으면 전체 번호 + 종류 + 통지일에 추가 근거를 결합하되, 날짜만 같은 복수 행은 자동 병합하지 않는다.

**기일과 종류별 차수는 통지 키에서 제외한다.** 기일 연장·정정이나 차수 정정이 동일 통지를 새 통지로 만들지 않도록 한다. 임시 후보가 정식 통지 키로 승격될 때는 기존 후보와 원자적으로 연결한다.

첨부 버전은 검증된 첨부 목록과 각 파일의 SHA-256으로 관리한다. 완료 건의 늦게 도착한 두 번째 메일은 다운로드를 다시 실행하지 않는다. 새 첨부·파일 수정·기일 변경은 같은 통지의 변경 후보로 기록한다. 기존 ZIP을 조용히 덮어쓰지 않으며, 변경을 확인한 뒤 새 버전 게시와 이전 파일 처리를 함께 결정한다.

이미 intake에서 ZIP을 다른 곳으로 옮겼더라도 완료 이력이 있으면 자동 재생성하지 않는다. 사용자가 재다운로드를 요청한 경우에만 별도 복구 실행으로 남긴다. 기존 이력이 없는 동명 파일은 덮어쓰거나 임의로 `(1)`을 붙이지 않고 충돌로 표시한다.

## 5. 차수·날짜와 ZIP 내용

### OA 차수

- EasyPAT에 확인 가능한 명시 차수가 있으면 우선 사용한다.
- 없으면 전체 진행 이력에서 중복·정정·재발행을 제거한 실제 의견제출통지 건을 통지일 순서로 세는 규칙을 제안한다.
- 보정요구·우선심사 보완·거절결정은 OA 차수에 포함하지 않는다.
- 과거 기록 누락, 동일 일자 복수 통지, 재심사 이후 차수 기준 미확정은 사용자 확인 대상으로 둔다. 메일 수나 다운로드 수로 차수를 추정하지 않는다.
- 거절결정은 OA 차수에 포함하지 않고 `거절결정서` 진행행만 별도로 통지일순으로 세어 `1차`, `2차`로 표시한다.
- 같은 진행번호와 통지일의 중복·정정 행은 한 건으로 계산한다. 목표 진행행이 종류별 이력에서 유일하게 식별되지 않으면 차수를 추정하지 않고 보류한다.

### 날짜

- 통지일은 해당 진행행의 `noticeDate`로 확인하고 원문 통지서와 대조한다. `recordDate`·메일 수신일은 대체 통지일로 자동 사용하지 않는다.
- 마감기일은 해당 통지에 연결된 EasyPAT 기일을 원문·메일과 대조한다. `dueDate`, `opinionDueDate`, `briefDueDate`의 실제 업무 의미를 확인하고 내부기일과 구분한다.
- 통지일에 일정 개월을 더하는 방식으로 기일을 계산하지 않는다. 날짜 형식 검증과 법적 기일 판단은 구분한다.
- 기일이 없거나 서로 다르면 원문별 값을 보존하고 검토 대기로 둔다. 기존 사용자 확정값을 자동 변경하지 않는다.

P261487의 OA 차수가 1로 검증된다면 예상 이름은 다음과 같다.

```text
[P261487] 1OA (2026-09-11)(2027-01-11).zip
```

### ZIP 내용

- 해당 통지서 본문, 연결된 인용문헌, 별지 및 기타 첨부 전체를 포함한다. 사건의 과거 계약서·명세서·다른 OA 파일은 섞지 않는다.
- 원본 파일명을 유지하며 동명 파일은 ZIP 내부 하위 경로로 구분한다. 동일 내용은 해시로 식별하고 원래 연결 관계를 목록에 남긴다.
- ZIP의 비ASCII 항목명은 UTF-8 플래그로 기록하고 중앙 디렉터리를 다시 검사한다. 한글 파일명이 UTF-8로 표시되지 않거나 추출본 이름·해시가 원본과 다르면 게시하지 않는다.
- `download-manifest.json`에 사건번호, 통지 종류·차수, 두 날짜, 원본 파일명, 크기, 해시, 확인 시각을 기록한다. 메일 원문·연락처·서버 내부 경로는 포함하지 않는다.
- EasyPAT가 ZIP을 제공하면 그 안의 파일 목록도 검사한다. 여러 원본 중 하나인 ZIP은 원본을 보존하고 최종 패키지에서 누락 없이 추적한다. 추출하는 구현에서는 경로 이탈·과도한 압축 해제를 차단한다.
- 본문 필수 파일이 없거나, 인용문헌 연결을 완전히 확인하지 못했거나, 한 파일이라도 다운로드 검증이 실패하면 ‘일부 다운로드’로 남기고 intake에 완료 ZIP을 게시하지 않는다.

## 6. 현재 연동의 보완 필요사항

기존 `easypat-automation`의 인증·정확 사건 조회·진행항목 첨부 다운로드를 재사용한다. 별도 OpenAI API 앱이나 외부 서비스를 만들 필요는 없다.

## 7. 저장·실행·복구 설계

- 운영 원장은 기존 로컬 SQLite에 통지 건, 근거 메일 연결, 첨부 버전, 패키지 작업 이력 테이블을 추가하는 안을 사용한다. ZIP 이름을 유일한 처리 원장으로 삼지 않는다.
- 상태 예: `접수 후보 → 원본 확인 → 첨부 확인 대기/검토 필요 → 다운로드 중 → ZIP 검증 → 게시 대기 → 완료`. 조회 실패·일부 다운로드·게시 실패는 별도 사유를 갖는다.
- 구성 예: `notice`, `notice_mail_link`, `notice_attachment`, `download_job`, `download_package`. 통지 키와 패키지 버전에 유일 제약을 두고 동시 실행을 막는다.
- ZIP은 먼저 비동기화 staging에서 만든 뒤 항목 수·크기·CRC·해시를 검사한다. 목적지에 최종 이름과 구별되는 임시 파일로 복사·검증하고, 같은 디렉터리에서 덮어쓰기 없는 이름 전환으로 게시한다.
- 파일 게시와 DB 완료 기록 사이의 중단은 manifest·해시로 복구한다. 최종 ZIP만 생기고 완료 기록이 빠진 경우에 두 번째 ZIP을 만들지 않는다.
- OneDrive의 로컬 게시 성공과 클라우드 동기화 완료는 별개다. 완료 기준은 지정 로컬 폴더의 검증된 ZIP 존재이며 클라우드 동기화 성공으로 표시하지 않는다.
- 저장 위치는 설정으로 고정하고 임의 메일 내용으로 바꾸지 않는다. 경로는 `-LiteralPath` 또는 동등한 리터럴 경로 API로 처리하며 대괄호가 와일드카드로 해석되지 않게 한다.
- 잠김·디스크 부족·권한 부족이면 원본과 staging을 보존하고 실패 사유를 남긴다. 사용자 파일을 삭제하거나 기존 폴더를 덮어쓰지 않는다.

### 실행 방식 제안

1. 1단계: 사용자가 `통지 다운로드 미리보기`를 요청하면 종류·대상·근거·예상 이름·첨부 수·보류 사유만 표시하는 dry-run.
2. 2단계: 실제 다운로드 검증을 통과한 후 `통지 다운로드 실행`으로 준비된 OA 또는 거절결정 건만 처리. 거절결정은 아래 별도 활성화 기준을 통과하기 전까지 미리보기만 허용한다.
3. 3단계: 별도 구현·운영 설정 시 매일 오전 9시 `Asia/Seoul` 예약 작업을 제안한다. 실행은 가장 이른 미완료 메일부터 재개 가능한 큐를 처리하며 예약일별 중복 잠금을 사용한다. 이번 기획에서 예약 작업을 만들지 않는다.

Outlook 신규수신 이벤트에 의존하지 않고 매일 정시 지정 폴더를 대조한다. 마지막 연속 완료 커서와 가장 이른 미완료 통지 메일 중 더 이른 시점부터 전날 0시까지 넓혀 다시 읽고, 종결된 메일은 중복 키로 건너뛴다. 최초 실행은 복구 시작점과 대상 목록을 dry-run으로 먼저 확정한다.

현재 EasyPAT 자동 재시도 금지 정책을 유지한다. 실패한 서버 요청은 같은 실행에서 반복하지 않는다. 다음 일자의 예약 실행은 저장된 마지막 안전 단계에서 새 시도 번호로 한 번 재개하며, 입력 해시가 같은 결정적 보류는 서버에 반복 요청하지 않는다.

## 8. 판단 근거와 사용자 검토

- 번호·날짜·정형 본문·중복 판단은 코드로 수행한다. 이번 표본의 명시 필드는 규칙 추출로 충분하다.
- 애매한 메일 사실은 `mail_intake`(gpt-5.6-terra/high), 사건 연결은 `matter_linker`(gpt-5.6-terra/high), 기일·사건 충돌은 `risk_verifier`(gpt-5.6-sol/high) 후보 검증을 사용한다. 실제 실행 설정은 `config/llm-routing.toml`을 읽는다.
- 모든 규칙·모델 후보를 표시하거나 반영하기 전에 입력 스냅샷, `decision_run`, 필드별 `decision_item`과 근거를 연결한다. 자동 처리 성공과 사용자가 검토한 정답은 구분한다.
- 사용자 수락·수정·거절은 `user_feedback`과 확정 `event`로 별도 기록한다. 다운로드 완료는 OA 대응 완료나 제출 완료를 뜻하지 않는다.
- 전용 `/downloads`에 사건번호, 종류·차수, 통지일, 마감기일, 연결 메일 수, 첨부 검증 수, ZIP 이름, 단계, 보류 사유와 재개 지점을 표시한다. 모호한 건의 판단은 `/analysis`로 연결한다. 상세 계약은 [통지서 자동 다운로드 대시보드 기획](./NOTICE_DOWNLOAD_DASHBOARD_PLAN.md)을 따른다.
- ZIP 게시 뒤 중간사건 대응 프로젝트를 새로 만드는 폴더·Codex 작업·사용자 승인 흐름은 [통지 종류별 대응 프로젝트 생성·진행 기획](./NOTICE_RESPONSE_PROJECT_WORKFLOW.md)을 따른다.
- 운영 알림은 새 다운로드 완료·실패·확인 필요 등 의미 있는 변화에 한한다.

## 9. 구현 순서와 검수 기준

**우선순위 1 — 실제 첨부 경로 검증: 완료.** 2개 사건의 첨부 0건 원인과 3개 사건의 조회 오류를 해결했다. 실제 OA 5건에서 통지서·인용문헌·HDR ZIP·특허청 `.fin`을 연속 묶음으로 찾았고 사건 첨부 집계와 목록 수를 모두 대조했다.

**우선순위 2 — 회차 선택·dry-run: 현재 표본 완료.** 사건 첨부 조회를 8번째 MCP 도구로 연결하고 5건을 재검증했다. 통지키, OA 차수, 기일 대조, 중복 원장 5개 테이블과 예상 ZIP 목록을 구현했다. Outlook 10통은 통지 5건으로 묶였고 모두 1OA·새 통지·준비 상태이며 첨부 합계는 33건이다. 실제 2OA·거절결정 표본은 아직 없어 합성 회귀만 통과했다.

**우선순위 3 — 다운로드·ZIP·복구: 수동 단건 경로 완료.** 회차별 staging, 직전 목록 재검증, 파일 길이·시그니처·해시 확인, ZIP 목록·UTF-8 항목명·추출본 해시 재검증, 무덮어쓰기 게시와 원장 기록을 연결했다. P261252 1차 OA로 실제 게시·중복 차단·한글 원본명 보존을 검증했다. 자동 큐의 중단 복구와 여러 건 일괄 재개는 우선순위 4와 함께 남아 있다.

**우선순위 4 — 운영 실행:** 수동 실행 검증 후 정기 실행, Outlook 종료 시 대기, 재로그인 후 이어서 처리, 대시보드 상태 표시를 연결한다.

필수 회귀 사례:

- 두 메일의 수신 순서가 바뀌거나 몇 일 떨어져도 같은 통지이면 ZIP 1개.
- 한 종류의 메일만 와도 원본 근거가 충분하면 처리 가능.
- 같은 사건의 1OA·2OA, 거절결정은 서로 구분하며 복수 동일명 진행행을 정확히 선택.
- 기존 10통은 5개 접수 후보로 집계되고 5개 모두 현재 통지 첨부 묶음·1OA 차수·통지키·중복 상태·예상 ZIP명을 확인한다. 별도 지정한 P261252 1차 OA는 실제 다운로드·파일 해시·ZIP 검증·게시까지 완료했다.
- 통지일과 수신일 차이, 기일 충돌, 차수 미상은 잘못된 파일명으로 게시하지 않음.
- 담당자 재지정·독촉·과거 메일 이동·기일 정정은 새 접수로 중복 생성하지 않음.
- 첨부 추가·수정, 동명 파일, 목록 변경, 파일 손상, 중간 실패, 동시 실행, 파일 게시 후 DB 기록 전 종료에 대해 중복·누락 방지.
- 인용문헌 하나가 실패하면 완료하지 않음. 기존 intake 파일은 덮어쓰지 않음.
- 메일 읽음 상태·위치와 EasyPAT 서버 데이터 불변 확인.

구현 완료 시 프로젝트 공통 조건을 적용한다: `dashboard`에서 `npm ci`, `npm run lint`, `npm run test:phase1`, `npm run test:phase2`, `npm run test:phase3`, `npm run test:phase4`, `npm run build`; `easypat-automation`의 영향받는 회귀 검증; 로컬 `127.0.0.1:4173`의 `/`, `/mail`, `/matters`, `/analysis`, `/wiki`, `/provisional`, `/api/projects`, `/api/matters`, `/api/work-db/status`, `/api/mail-sync`, `/api/analysis`, `/api/wiki` 정상 응답. 이번 변경은 기획 문서이므로 해당 구현 검증을 수행한 것으로 주장하지 않는다.

## 10. 거절결정서 자동 다운로드 확장 계획

### 10.1 자동 실행 후보가 되는 조건

거절결정은 지정 Outlook 폴더를 주기 대조할 때 다음 조건을 모두 충족한 메일만 후보로 만든다.

1. 중복 제거된 새 메일이며 제목이 `[업무요청]`으로 시작하고 제목 또는 본문에 `거절결정서`가 명시돼 있다.
2. 제목과 본문 전체에서 유효한 당소관리번호 전체 문자열이 정확히 하나만 확인된다. 접미사를 삭제하거나 비슷한 사건과 병합하지 않는다.
3. 메일에 대응기한이 하나만 있고 유효한 날짜로 해석된다.
4. `[EASYPAT_S] ... 업무담당자로 지정되었습니다.` 메일은 보조 근거로만 연결한다. 이 메일 하나만으로 다운로드를 시작하지 않는다.
5. 회신, 독촉, 대응 초안 송부, 제출 완료, 거절결정 취소·정정 안내는 새 거절결정 접수의 단독 트리거로 사용하지 않는다.

후보가 생겨도 즉시 파일을 받지 않는다. EasyPAT에서 아래 조건을 모두 다시 확인한 경우에만 `ready`로 승격한다.

- 정확 사건 검색에서 당소관리번호 전체 문자열이 일치하는 사건이 하나다.
- 진행기록의 문서명이 정확히 `거절결정서`이고, 진행번호와 통지일로 한 행이 유일하게 식별된다.
- EasyPAT 마감기일이 존재하며 메일의 대응기한과 일치한다. 기일은 통지일로부터 계산하지 않는다.
- 사건 첨부 저장소에서 사건번호를 포함하고 `거절결정서.pdf`로 끝나는 본문 파일이 통지일 당일부터 7일 이내에 등록된 유일한 최근 후보다.
- 본문과 연결된 가장 가까운 선행 HDR ZIP, 같은 묶음의 별지·인용문헌·기타 첨부와 `.fin`이 하나의 연속 구간으로 검증된다.
- 첨부가 한 건 이상이고 전체 목록 수, 파일명, 등록시각, 크기가 유효하다.
- 동일 통지키의 완료 패키지가 없고 목적지에 원장과 무관한 동명 ZIP이 없다.

두 안내메일의 도착 순서와 시간 차이는 실행 조건이 아니다. 업무요청 메일 하나만 있어도 EasyPAT 원본이 모두 일치하면 처리할 수 있다. 같은 사건에 OA와 거절결정 업무요청이 함께 있으면 종류별로 별도 후보를 만들고, 종류가 없는 담당자 지정 메일을 임의로 어느 한쪽에 귀속하지 않는다.

### 10.2 식별·파일명·중복 규칙

- 통지 종류는 `rejection_decision`, EasyPAT 진행항목명은 `거절결정서`로 저장한다.
- 거절결정은 OA 차수를 갖지 않으며 `oa_sequence`는 `NULL`로 둔다. 별도 `rejection_sequence`에 `거절결정서` 진행행만 센 1부터 시작하는 차수를 저장한다.
- 확정 통지키는 `당소관리번호 전체 + rejection_decision + EasyPAT 진행번호 + 통지일`이다.
- 진행번호가 없으면 통지일만으로 자동 완료하지 않고 `identity_unresolved`로 보류한다.
- 파일명은 `[당소관리번호 전체] 거절결정 (n차)(통지일)(마감기일).zip`으로 고정한다. 예: `[P261487] 거절결정 (2차)(2026-10-01)(2027-02-01).zip`.
- 같은 사건에 서로 다른 거절결정이 있으면 진행번호와 통지일로 원장에서는 구분한다. 같은 통지일·같은 최종 파일명이 충돌하면 자동으로 `(1)`을 붙이지 않고 검토 대상으로 둔다.
- 완료 원장이 있으면 메일이 다시 오거나 ZIP이 intake 밖으로 이동돼도 재생성하지 않는다. 첨부 목록이나 기일이 바뀌면 기존 결과를 덮어쓰지 않고 새 패키지 버전 후보로 기록한다.

### 10.3 다운로드와 ZIP 검증

OA에서 검증된 동일 출처·용량·무덮어쓰기 정책을 그대로 적용한다. 다운로드 직전에 거절결정 첨부 목록을 다시 조회하고 최초 스냅샷과 완전히 일치해야 한다. 각 파일은 길이·콘텐츠 형식과 SHA-256을 확인하고, PDF와 ZIP은 시그니처도 확인한다.

최종 ZIP에는 거절결정서 본문, 연결된 HDR ZIP, 별지·인용문헌·기타 첨부 전체, 특허청 원본 파일과 `download-manifest.json`을 넣는다. 원본 파일명을 유지하고 비ASCII 항목명은 UTF-8 플래그를 검증한다. ZIP을 별도 validation 폴더에 추출해 항목명·개수·크기·해시를 원본과 다시 대조한 뒤에만 intake에 게시한다. 한 파일이라도 실패하면 최종 ZIP을 게시하지 않는다.

manifest에는 `noticeKind: rejection_decision`, `rejectionSequence`, 통지일, 마감기일, EasyPAT 진행번호, 원본별 파일명·크기·해시와 확인 시각을 기록한다. OA 차수 필드는 `null`로 명시하고 메일 원문, 서버 내부키와 업로드 경로는 넣지 않는다.

### 10.4 구현 작업

1. 공통 실행 입력을 `noticeKind` 중심으로 바꾸고 OA의 `oaSequence`와 거절결정의 `rejectionSequence`·`noticeDate`·`progressSequence` 선택을 분리한다.
2. OA에 고정된 실행기·원장 검증·ZIP 게시기의 `opinion_submission` 검사를 허용된 두 종류의 명시적 분기로 바꾼다. 파일명 생성은 한 함수에서 종류별로 결정한다.
3. 거절결정 첨부 선택기는 기존 연속 묶음 알고리즘을 재사용하되 실제 표본에서 본문 파일명, HDR 선행 간격, 인용문헌과 `.fin` 배치를 검증한 뒤 관찰된 범위만 허용한다.
4. Outlook 미리보기를 메일 한 건별 후보로 만든 뒤 EasyPAT 진행번호와 통지일에 연결한다. 현재의 `사건번호+종류` 단순 묶음은 같은 사건의 복수 거절결정을 합칠 수 있으므로 운영 실행에는 사용하지 않는다.
5. 작업 잠금과 재개 키를 통지키에 걸고, `candidate → ready → downloading → validating → published` 전이를 원장에 기록한다. 실패 원인과 마지막 안전 체크포인트를 남긴다.
6. 대시보드 문서 수집 화면에 종류 `거절결정`, 근거 메일, 진행번호, 날짜 대조, 첨부 수, 예상 ZIP명, 보류 사유와 재개 상태를 표시한다.
7. Outlook 일일 예약 작업은 위 단계가 실제 표본 검증을 통과한 뒤 활성화한다. 같은 실행에서 네트워크 실패를 자동 재시도하지 않으며 다음 일자 실행은 실패 상태를 그대로 반복하지 않고 마지막 안전 단계와 재개 가능 여부를 먼저 판정한다.

### 10.5 활성화 순서와 검수 기준

1. **합성 회귀:** 거절결정 1차·2차, 같은 사건의 OA와 거절결정 동시 존재, 같은 사건의 복수 거절결정, 메일 중복·기일 충돌·진행번호 누락·차수 미확정·동명 파일 충돌을 검증한다.
2. **실제 읽기 검증:** 실제 거절결정 사건을 최소 3건 확보해 진행행과 사건 첨부 저장소를 MCP로 읽기 전용 조회한다. 본문만 있는 묶음, 인용문헌이 있는 묶음, 같은 사건에 과거 OA가 있는 묶음을 포함하는 것이 목표다.
3. **수동 dry-run:** 예상 파일명과 포함 파일 목록을 사용자에게 제시하고 파일 GET·DB 쓰기·ZIP 생성을 하지 않는다.
4. **수동 단건 게시:** 사용자가 지정한 한 건으로 실제 다운로드, UTF-8 ZIP 검증, 무덮어쓰기 게시, 원장 중복 차단과 재실행 `duplicate`를 확인한다.
5. **제한 운영:** 확정된 가장 이른 미완료 메일부터 매일 오전 9시 자동 후보 생성과 준비 건 게시를 실행한다.

다음 중 하나라도 발생하면 자동 게시하지 않고 보류한다: EasyPAT 진행행 복수 일치, 메일·EasyPAT 기일 불일치, 진행번호 없음, 본문 PDF 없음 또는 복수 후보, HDR ZIP 없음, 첨부 묶음 경계 불명확, 목록 재조회 변경, 파일 검증 실패, 완료 원장과 실제 파일 불일치, 목적지 동명 파일 충돌. 실제 거절결정 표본 검증 전에는 합성 테스트 통과만으로 운영 자동 다운로드를 활성화하지 않는다.
