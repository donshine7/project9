# Outlook 통지 메일 자동 다운로드 트리거 기획

작성: 2026-09-21. 상태: **직접 수신인 증거 수집·결정적 메일 파서 구현 완료, 일일 감지 실행과 자동 게시 비활성**.

## 1. 목표와 필수 수신인 조건

Outlook의 `jtjang@sspat.net` 저장소에 수신된 다음 세 종류의 메일을 감지해 EasyPAT 문서 다운로드 후보를 만든다.

| 메일·EasyPAT 문서 | 내부 통지 종류 | 결과 파일명 |
|---|---|---|
| 의견제출통지서 | `opinion_submission` | `[사건번호] nOA (통지일)(마감기일).zip` |
| 거절결정서 | `rejection_decision` | `[사건번호] 거절결정 (n차)(통지일)(마감기일).zip` |
| 우선심사신청보완요구서 | `priority_exam_supplement_request` | `[사건번호] 우선심사 보완 (n차)(통지일)(마감기일).zip` |

**필수 조건은 받는 사람(To)에 장진태가 직접 포함되는 것이다.** Outlook의 수신자 객체를 열거해 `Recipient.Type = olTo`인 항목 중 다음 기준으로 동일 인물을 확인한다.

1. SMTP 주소가 해석되면 `jtjang@sspat.net`과 정확히 일치해야 한다.
2. SMTP 주소를 해석할 수 없는 경우에만 표시명이 공백 정규화 후 `장진태`와 정확히 일치하고, 대상 저장소가 `jtjang@sspat.net`인지 함께 확인한다.
3. CC에만 장진태가 있거나 `국내관리팀` 같은 배포 목록만 To에 있는 메일은 자동 다운로드 트리거가 아니다.
4. 전달·회신 본문이나 인용된 원문에 `장진태`가 적혀 있는 것은 수신인 근거로 사용하지 않는다.
5. 보낸 편지함, 임시 보관함, 일정, 작업과 연락처 항목은 대상이 아니다.

구조화된 수신자 스냅샷에는 유형(`to`/`cc`), 표시명, 해석된 SMTP 주소와 해석 성공 여부를 기록하고 해시를 남긴다. 자동 실행 판단은 단순한 `MailItem.To` 문자열이나 본문 검색이 아니라 이 스냅샷의 직접 To 일치 결과를 사용한다.

## 2. 감지할 메일 형식

### 업무요청 메일

제목의 공백과 NBSP만 정규화한 뒤 다음 형식을 판정한다. 대괄호 안의 전체 당소관리번호는 제목과 현재 작성 본문에서 정확히 하나여야 한다.

- `[업무요청]의견제출통지서대응 [당소관리번호/의뢰인]`
- `[업무요청]거절결정서대응 [당소관리번호/의뢰인]` 또는 실제 표본에서 확인된 `거절결정서 접수` 형식
- `[업무요청]우선심사신청보완요구서대응 [당소관리번호/의뢰인]`

`대응 요청`처럼 이미 관찰된 어미 변형은 고정 허용 목록으로 관리한다. 단순히 제목 어디엔가 문서명이 포함됐다는 이유로 후보를 만들지 않는다.

### EasyPAT 담당자 지정 메일

제목이 `[EASYPAT_S] [당소관리번호]...업무담당자로 지정되었습니다.` 형식이고 현재 본문의 `OurRef`가 같은 전체 번호이며, `업무내용` 또는 `담당자업무`가 세 문서명 중 하나와 정확히 일치할 때 보조 근거로 사용한다. `담당자가 변경되었습니다`, 담당 해제, 독촉과 일반 안내는 새로운 통지의 단독 근거가 아니다.

업무요청과 담당자 지정 메일 중 하나가 먼저 와도 후보를 만들 수 있다. 두 번째 메일이 나중에 오면 기존 통지 후보에 연결하고 새 다운로드 작업을 만들지 않는다. 업무요청 메일에 대응기한이 있으면 EasyPAT 기일과 반드시 일치해야 한다. 기일이 없는 담당자 지정 메일만 먼저 온 경우에는 EasyPAT의 유일한 미처리 진행행과 기일을 확인할 때까지 후보 상태로 둔다.

### 트리거가 아닌 메일

- `[리마인더]`, 재요청, 독촉, 담당자 변경
- 대응 방향, 의견서·보정서·번역문 초안 송부
- 고객 회신, 제출 완료, 접수 완료, 처리 완료
- 제목이나 새 본문에 유효한 전체 당소관리번호가 없거나 둘 이상인 메일
- 과거 인용문에만 업무요청 제목이 있는 회신·전달 메일
- 직접 To가 아닌 CC·BCC·배포 목록 수신 메일

## 3. 매일 정시 감지 구조

기존 `Application_NewMailEx`는 메일 분류와 폴더 이동만 담당한다. 이 이벤트 안에서 EasyPAT 로그인, 네트워크 요청, 파일 다운로드나 ZIP 생성을 실행하지 않는다. 메일 한 건마다 즉시 작업을 시작하지 않고 다음 정시 실행에서 모아서 처리한다.

1. **예약 시각:** 기본값은 매일 오전 9시 `Asia/Seoul`이다. `dailyRunTime`과 시간대는 설정으로 관리하며 변경 이력을 남긴다.
2. **한 번만 실행:** 같은 예약일의 실행키와 DB 잠금을 사용해 수동 실행·작업 스케줄러 중복 기동이 있어도 한 작업만 실행한다.
3. **폴더 고정:** 최초 설정에서 Outlook StoreID와 `국내특허 OA/ 우선심사 보완` 폴더 EntryID를 확인해 저장한다. 표시명이 같은 삭제 폴더나 다른 저장소는 읽지 않는다.
4. **정시 대조:** 매일 실행 시 복구 시작점부터 실행 시각까지 대상 폴더를 읽기 전용으로 대조한다. `NewMailEx`와 `ItemAdd`는 다운로드나 조기 실행 신호로 사용하지 않는다.
5. **읽음 상태 비의존:** `UnRead` 값을 필터로 사용하지 않고 읽음 상태를 변경하지 않는다. 메일을 이동·삭제·분류하지도 않는다.
6. **놓친 예약 실행:** Windows 작업 스케줄러는 예약 시각을 놓치면 사용자가 로그인한 다음 가능한 시점에 한 번 실행하도록 설정한다. 이미 해당 예약일 실행이 완료됐으면 다시 실행하지 않는다.

Outlook이 종료됐거나 COM 접근이 실패하면 `outlook_unavailable`로 해당 일자의 실행을 끝낸다. Outlook을 강제로 실행하지 않으며 다음 예약 실행은 같은 복구 시작점을 유지한다.

### 중단 지점부터 다시 감지

활성화 시각 이전 메일을 일괄 `seen_before_activation`으로 넘기지 않는다. 매일 실행은 다음 값 중 가장 이른 시각을 `recoveryFrom`으로 정한다.

1. 마지막으로 **연속 처리 완료**가 확인된 메일 커서 다음 시각
2. `published`, `duplicate`, `not_target` 중 어느 종결 상태에도 도달하지 못한 가장 이른 대상 메일의 수신시각
3. `candidate`, `source_verified`, `ready`, `downloading`, `validating`, `held`, `failed` 상태인 작업에 연결된 가장 이른 원본 메일의 수신시각
4. 이전 실행이 메일 목록을 읽는 중 중단됐다면 그 실행의 `scanFrom`

`recoveryFrom` 전날 0시부터 한 번 더 중첩 조회해 같은 시각의 메일, 늦은 폴더 이동과 Outlook 정렬 차이를 흡수한다. 이미 종결된 메일은 안정 키와 통지키로 즉시 건너뛰므로 ZIP을 다시 만들지 않는다.

최초 실행에 기존 커서가 없으면 현재 DB와 대상 폴더를 읽기 전용으로 대조해 **직접 To 장진태 조건을 충족하면서 완료 통지에 연결되지 않은 가장 이른 메일**을 복구 시작점으로 제안한다. 먼저 해당 시작일·후보 수·예상 작업을 dry-run으로 저장하고, 그 결과가 확정된 뒤 같은 시작점으로 실제 예약 실행을 활성화한다. 따라서 자동화 도입일보다 먼저 도착했지만 아직 처리되지 않은 메일도 누락하지 않는다.

전역 스캔 커서는 폴더 열거와 후보 upsert가 모두 커밋된 뒤에만 전진시킨다. 개별 통지는 별도 상태를 가지므로 한 건이 보류돼도 뒤 메일의 발견을 막지 않는다. 다만 가장 이른 미완료 시점은 보존해 다음 날 다시 대조한다.

### 단계별 재개

다음 날의 예약 실행은 미완료 작업을 먼저 점검한 뒤 새 메일을 처리한다.

- `candidate`·`held`: 새 짝 메일 또는 EasyPAT 증거가 생겼는지 확인한다. 입력 해시가 같고 보류 사유도 결정적이면 네트워크 요청을 반복하지 않고 상태만 유지한다.
- `source_verified`·`ready`: 다운로드 직전 목록 재검증부터 이어간다.
- `downloading`: 기존 staging과 manifest를 검사하고 검증된 파일을 보존한다. 목록이 같을 때만 누락 파일부터 새 작업 시도로 이어간다.
- `validating`: 이미 만든 ZIP과 추출본을 다시 검증한다.
- 최종 ZIP이 게시됐지만 DB 완료가 빠진 경우: 파일명·크기·SHA-256과 manifest가 일치하면 새 ZIP을 만들지 않고 원장만 복구한다.
- 일시적인 Outlook·EasyPAT·네트워크 실패: 다음 일자 실행에서 새 시도 번호로 한 번 재개한다. 같은 실행 안에서 반복 요청하지 않는다.

예약 실행마다 `scheduledFor`, `recoveryFrom`, `scanTo`, 마지막 안전 단계와 시도 번호를 기록한다. `completed`는 해당 구간의 메일 발견·후보 기록과 실행 가능한 작업 처리가 모두 끝났을 때만 부여하고, 보류 건이 있으면 실행 요약에 계속 표시한다.

## 4. 메일 중복과 통지 병합

메일 자체의 안정 키는 `InternetMessageID`를 우선하고, 없으면 StoreID·EntryID와 정규화 제목·수신시각·본문 해시를 결합한다. 같은 Message-ID의 재수집은 한 메일로 처리한다.

메일은 바로 ZIP 작업이 아니라 통지 후보에 연결한다. 통지키는 다음과 같다.

```text
전체 당소관리번호 + 통지 종류 + EasyPAT 진행번호 + 통지일
```

메일 도착 시점에는 진행번호와 통지일이 없을 수 있으므로 임시 후보 키를 사용하고, EasyPAT 확인 후 확정 통지키로 원자적으로 승격한다. 같은 사건의 OA·거절결정·우선심사 보완은 종류가 다르므로 합치지 않는다. 같은 종류의 다음 차수도 EasyPAT 진행번호와 통지일로 구분한다.

한 메일이 먼저 자동 다운로드를 완료한 뒤 짝 메일이나 리마인더가 도착하면 `notice_mail_link`만 추가하고 작업은 `duplicate`로 끝낸다. intake에서 ZIP을 옮겼더라도 완료 원장이 있으면 자동 재생성하지 않는다.

## 5. EasyPAT 확인과 실행 승인

수신인과 메일 형식을 통과해도 즉시 다운로드하지 않는다. 작업자는 다음 조건을 순서대로 검증한다.

1. 당소관리번호 전체 문자열이 정확히 일치하는 EasyPAT 사건이 하나다.
2. 문서 종류에 맞는 진행행이 존재한다.
   - 의견제출통지서: `rec_doc = 의견제출통지서`
   - 거절결정서: `rec_doc = 거절결정서`
   - 우선심사 보완: `rec_doc = 우선심사신청보완요구서`
3. 메일의 대응기한이 있으면 `d_due`와 일치하는 미완료 진행행이 하나다.
4. 메일에 기일이 없으면 수신일 이전 또는 당일에 통지되고 수신일과 가까운 미완료 진행행이 유일해야 한다. 임의 기간으로 법적 기일을 계산하지 않으며, 후보가 복수이면 보류한다.
5. OA·거절결정은 사건 첨부 저장소, 우선심사 보완은 검증된 관련 탭에서 본문과 연결 첨부의 경계를 확인한다.
6. 동일 통지키의 완료 패키지가 없고 목적지에 원장과 무관한 동명 파일이 없다.
7. 각 문서 종류의 실제 다운로드 기능이 운영 활성 상태다. 아직 실제 표본 검증 전인 종류는 자동 감지하더라도 `feature_not_enabled`로 보류한다.

차수는 종류별 진행행만 통지일순으로 센다. OA의 `nOA`, 거절결정의 `n차`, 우선심사 보완의 `n차`는 서로 영향을 주지 않는다. 같은 진행번호와 통지일의 중복·정정 행은 한 건으로 계산하고 목표 행이 유일하지 않으면 게시하지 않는다.

## 6. 자동 다운로드와 게시

`ready`로 승인된 후보만 기존 안전 다운로드 경로에 전달한다. 다운로드 직전에 EasyPAT 첨부 목록을 다시 읽어 최초 스냅샷과 위치·문서명·파일명·등록시각·크기가 모두 같은지 확인한다.

- 파일당 최대 64 MiB, 패키지 최대 512 MiB
- 고정된 EasyPAT HTTPS 출처와 검증된 업로드 경로만 허용
- HTTP 200, Content-Length, MIME, PDF·ZIP 시그니처와 SHA-256 확인
- staging에서 ZIP 생성 후 UTF-8 항목명, 항목 수, 추출본 크기·해시 재검증
- 고정 intake 폴더에 임시 파일을 검증한 뒤 원자적으로 게시
- 기존 최종 파일 덮어쓰기, `(1)` 자동 생성, 같은 실행의 네트워크 자동 재시도 금지

실패하면 staging과 원장을 보존하고 `held` 또는 `failed` 사유를 기록한다. 일부 파일만 받은 상태를 완료로 표시하지 않는다. EasyPAT 서버 데이터와 Outlook 메일은 수정하지 않는다.

## 7. 데이터와 감사 이력

메일 수집 시 기존 `mail_item`과 별도로 직접 To 판정에 사용한 구조화된 수신자 스냅샷 또는 동등한 불변 근거를 저장한다. 자동 트리거 기록에는 다음을 포함한다.

- 원본 메일 키와 수신시각, StoreID·Folder EntryID의 해시
- `recipientMatched = true`, 일치 방식 `smtp` 또는 제한된 `display_name_fallback`
- 통지 종류, 전체 당소관리번호, 파서 버전과 제목/새 본문 해시
- EasyPAT 진행번호·통지일·기일, 첨부 스냅샷 버전
- 실행 상태, 보류·실패 코드, 패키지 버전과 최종 SHA-256

본문 원문, 연락처, 쿠키, SQL, EasyPAT 내부키와 업로드 경로는 manifest에 넣지 않는다. 메일 후보 생성, EasyPAT 승인, 다운로드와 게시를 서로 다른 이벤트로 남겨 어느 조건에서 자동 실행됐는지 추적할 수 있게 한다.

웹 진행 상황은 전용 `/downloads` 화면에서 표시한다. 예약 시각·실제 실행 시각·`recoveryFrom`·`scanTo`, 통지별 현재 단계, 첨부 검증 수, ZIP 게시 결과, 보류 사유와 재개 지점을 원장에서 읽는다. 화면 조회 자체는 Outlook·EasyPAT 호출이나 다운로드를 시작하지 않는다. 화면·API·추가 이벤트 원장의 상세 계약은 [통지서 자동 다운로드 대시보드 기획](./NOTICE_DOWNLOAD_DASHBOARD_PLAN.md)을 따른다.

## 8. 실행 상태와 보류 코드

```text
mail_detected → recipient_verified → notice_candidate → source_verified
→ ready → downloading → validating → published
```

대표 보류 코드는 다음과 같다.

- `recipient_not_direct_to_jtjang`
- `unsupported_mail_template`
- `matter_reference_missing_or_ambiguous`
- `easypat_progress_missing_or_ambiguous`
- `mail_easypat_due_date_mismatch`
- `notice_sequence_unresolved`
- `attachment_package_missing_or_ambiguous`
- `fresh_attachment_list_mismatch`
- `destination_filename_conflict`
- `feature_not_enabled`
- `outlook_unavailable` 또는 `easypat_session_required`

`recipient_not_direct_to_jtjang` 메일은 다운로드 후보 수에 포함하지 않는다. 감사용 최소 메타데이터만 남기거나 기존 일반 메일 수집 결과를 참조한다.

## 9. 활성화 순서

1. **파서·수신인 회귀:** To 장진태, CC만 장진태, 배포 목록, 여러 수신인 중 장진태, SMTP 해석 실패, 인용문 속 이름을 구분한다. 세 종류의 업무요청·담당자 지정·리마인더를 검증한다.
2. **복구 범위 dry-run:** 원장과 대상 폴더에서 가장 이른 미완료 메일을 계산해 `recoveryFrom`, 후보 수와 예상 종류를 표시한다. EasyPAT GET·ZIP·intake 쓰기는 하지 않는다.
3. **EasyPAT dry-run:** 세 종류별로 실제 진행행·차수·기일·첨부 목록과 예상 파일명을 조회한다.
4. **종류별 수동 단건:** OA는 기존 P261252 경로를 회귀 검증하고, 거절결정과 우선심사 보완은 각각 실제 한 건의 게시·중복 차단을 먼저 확인한다.
5. **종류별 제한 활성화:** `opinion_submission`부터 자동 게시를 켜고, 실증이 끝난 순서대로 `rejection_decision`, `priority_exam_supplement_request`를 별도 기능 플래그로 활성화한다.
6. **대시보드 연결:** `/downloads` 읽기 화면에서 dry-run, 기존 완료 패키지와 단계 이벤트가 정확히 보이는지 먼저 검증한다.
7. **운영 전환:** 확정된 `recoveryFrom`부터 매일 오전 9시 정시 실행을 시작한다. 미완료 건을 먼저 재개하고 이어서 새 메일을 처리하며, 실패·보류·완료를 대시보드 문서 자동수집 화면에 표시한다.

## 10. 필수 회귀와 완료 기준

- 직접 To가 장진태인 메일만 후보가 되고 CC·BCC·배포 목록 수신은 제외된다.
- 두 안내메일의 순서가 바뀌거나 여러 날 떨어져도 같은 EasyPAT 통지이면 ZIP 하나다.
- 한 안내메일만 있어도 EasyPAT 원본이 유일하고 해당 종류의 기능이 활성화돼 있으면 처리할 수 있다.
- 같은 사건의 1OA·2OA, 거절결정 1차·2차, 우선심사 보완 1차·2차가 서로 분리된다.
- Outlook 종료, 예약 실행 누락, 분류 지연, 늦은 폴더 이동과 작업자 재시작 후 가장 이른 미완료 시점부터 복구되고 중복 다운로드가 발생하지 않는다.
- 읽음 상태·폴더 위치·Outlook 메일과 EasyPAT 서버 데이터가 변경되지 않는다.
- 다운로드 중단, 목록 변경, 파일 손상, 동명 충돌과 게시 후 DB 기록 전 종료를 복구해도 완료 ZIP이 중복 생성되지 않는다.
- `/downloads`의 단계와 파일 수가 원장과 일치하며 화면 새로고침은 Outlook·EasyPAT 요청을 발생시키지 않는다.
- `easypat-automation` 전체 회귀와 dashboard의 공통 lint·phase 테스트·build·필수 로컬 경로 응답이 성공한다.

이 문서는 자동 실행을 활성화하지 않는다. 복구 범위 dry-run 결과와 종류별 실제 단건 게시 검증을 마친 뒤 기능 플래그와 일일 예약 작업을 하나씩 켠다.

## 11. 2026-09-21 구현 결과

- Outlook 읽기 전용 수집 결과에 받은 편지함 저장소 이름과 To·CC·BCC별 표시명, SMTP 주소, 주소 해석 여부를 구조화해 저장한다. 이 수집은 읽음 상태, 폴더 위치와 원본 메일을 변경하지 않는다.
- 세 문서 종류의 업무요청 제목과 EasyPAT 담당자 지정 제목·현재 본문을 판별하는 결정적 파서를 구현했다. 전체 당소관리번호를 보존하며, 직접 To가 `jtjang@sspat.net`이거나 제한된 표시명 대체 조건에서 정확히 `장진태`인 메일만 통과한다.
- CC·BCC만 일치하는 메일, 배포 목록, 다른 저장소, 회신·전달문의 인용 부분, 사건번호 복수 또는 모호한 제목은 후보에서 제외하는 회귀 검증을 추가했다.
- 파서와 수신인 증거는 구현됐지만 실제 Outlook 폴더를 훑는 일일 실행기와 Windows 예약 작업은 아직 연결하지 않았다. 운영 설정의 `schedulerEnabled`와 `outlookDetectionEnabled`는 모두 `false`다.
