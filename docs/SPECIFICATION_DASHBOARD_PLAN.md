### 무엇을 어디에 복사하는가

기준 상위 경로는 `C:\ChatGPT\AI-Work\10_특허\한국특허명세서작성`이다. 아래의 ‘새사건폴더’는 `<당소관리번호전체>_<의뢰인식별명>`으로 정한다.

### 자동 생성과 수동 복사

기본 경로는 P2 dry-run → P3 초기화 도구 실행이다. 사람이 파일을 하나씩 골라 복사할 필요는 없다.
현재 harness.py의 init은 사건번호·프로젝트명·서비스·창작 방향과 샘플 해제 및 공통 기준 해시를 기록한다.
발명 유형·담당자 입력 반영은 향후 신규 초기화 어댑터에서 구현하거나 첫 사건 작업에 명시적으로 요청한다. 이미 구현된 입력 필드처럼 표시하지 않는다.

수동 경로에서는 P2의 동일 경로·복사 목록 확인 후 탐색기에서 샘플 전체를 복사하고 복사본의 이름을 바꾼다.
복사본 case.yaml의 case_id, project_name, service_type, invention_type, creation_direction, owner를 입력하고 is_template을 false로 바꾼다.
case.yaml은 JSON 호환 YAML이므로 구조와 따옴표를 유지한다. 편집이 어려우면 P6의 요청문에 ‘아래 확정값으로 이 신규 복사본만 초기화하라’를 포함한다.
수동 복사 후에는 기존 폴더를 거부하는 init --apply를 다시 실행하지 않는다. 읽기 전용 점검으로 확인하고, 사용자 지시를 받은 Codex가 신규 복사본의 메타데이터·기준 해시를 기록한다.
inputs, latest_outputs, approvals, review를 임의로 완료값으로 채우지 않는다. PROJECT.md에는 사람이 아는 배경·목표를 적고 분석 내용은 이후 Codex가 구분하여 작성한다.
수동 복사 경로도 필수 파일·샘플 해제·사건번호·공통 접근을 통과해야 준비 완료로 표시한다.

### Codex 프로젝트 폴더 설정

사람이 로컬 프로젝트를 추가한 뒤 프로젝트 편집에서 다음 두 폴더를 설정하도록 안내한다.

| 설정 | 지정할 절대 경로 |
|---|---|
| 기본 폴더 | `C:\ChatGPT\AI-Work\10_특허\한국특허명세서작성\새사건폴더` |
| 보조 폴더 | `C:\ChatGPT\AI-Work\10_특허\한국특허명세서작성\_shared` |
| 작업 위치 | 기본 폴더에서 시작하는 로컬 작업 |

사건 폴더를 기본으로 설정하고 그 사건 프로젝트에서 새 작업을 시작한다. 상위 한국특허명세서작성 폴더·샘플·_shared를 기본 폴더로 설정하지 않는다.
기존 상대 경로 `../_shared`를 유지하도록 이 운영에서는 원래 로컬 사건 폴더를 사용한다. 별도 worktree 구성은 이 시작 절차에 포함하지 않는다.
보조 폴더 스킬의 자동 발견을 가정하지 않고, 사건 AGENTS.md의 명시적 경로로 필요한 SKILL.md를 읽는다.
연결된 폴더는 앱에서 읽기·쓰기 대상이 될 수 있다. `_shared`의 ‘읽기 전용’은 사건 운영 지침이며 보조 폴더 추가만으로 OS 권한이 읽기 전용으로 설정되는 것은 아니다.
공통 자료를 읽을 수 없으면 원인을 확인하며, 해결을 위해 상위 전체 폴더나 다른 사건을 추가하지 않는다.
앱 버전에 따라 메뉴 이름이 달라지면 ‘사건 폴더를 primary, _shared를 secondary’라는 결과를 기준으로 안내한다.

공식 동작 확인: [OpenAI 프로젝트 및 작업 안내](https://learn.chatgpt.com/docs/projects) — 기본 폴더에서 새 작업이 시작되고 보조 폴더 지침·스킬은 자동 발견되지 않는 점을 기준으로 설계했다. 확인일 2026-09-21.

### 대시보드가 제공할 준비 단계 카드

각 카드에는 ‘누가 / 어디에서 / 무엇을 / 무엇으로 완료 확인’을 표시한다.
예를 들어 P4에는 기본 폴더 경로·보조 폴더 경로 각각의 복사 버튼, 설정 안내, ‘설정했음’ 체크, ‘실제 접근 미확인’ 표시를 둔다.
P5에는 자료 투입 경로 복사, 사람이 넣을 자료 목록, 투입 완료 확인, 실제 발견 파일 수를 보여준다. README나 빈 구조화 파일은 원본 투입 건수로 세지 않는다.
P6에는 사건 정보가 채워진 ‘첫 작업 지시문 복사’, 사용자가 입력하는 작업 연결 정보, 시작 점검 결과를 보여준다.
복사 버튼은 클립보드 복사만 수행하며 폴더 생성·Codex 프로젝트 생성·요청 전송이 실행됐다고 표시하지 않는다.
브라우저에서 탐색기 또는 Codex를 직접 열 수 있는 연결은 별도 검증 전 제공하지 않는다. 경로와 지시문 복사는 기본 제공한다.

첫 작업 지시문 구성:

```text
이 프로젝트의 기본 폴더는 [새사건폴더 절대 경로]이고 공통 폴더는 [공통 폴더 절대 경로]입니다.
사건번호 [전체 번호], 서비스 [메이킹 등], 발명 유형 [방법 등], 담당자 [이름]입니다.
창작 방향: [사람이 입력한 방향].
먼저 실제 작업 폴더와 AGENTS.md, case.yaml, PROJECT.md, STATUS.md, DECISIONS.md를 확인하세요.
사건 지침에서 지정한 공통 정책·스킬을 읽을 수 있는지 확인하고 자료 접수를 시작하세요.
수동 복사본이면 위 확정값으로 이 신규 복사본의 메타데이터와 기준 해시를 기록하세요.
10_source_original과 20_prior_art의 원본을 보존하면서 자료 목록·누락·충돌을 정리하고 다음 작업을 기록하세요.
다른 사건 폴더와 _eval은 참조하지 말고 _shared는 변경하지 마세요.
```

### 작성 중 사람이 하는 일

| 작성 시점 | 사람의 행위 | 대시보드 표시 |
|---|---|---|
| 접수·자료 정리 | 누락 자료 추가, 충돌한 사실 확인 | 질문·필요 자료·업로드 위치·확인자 |
| 창작·포인트 | 필요한 경우 창작 방향 선택 또는 보완 | 현재 지시와 선택 대안, 확정 이유 |
| 청구항·본문 | 실제 검토 의견과 수정 지시 | 대상 버전, 수정 이유, 반영 상태 |
| 검수 | 검수 결과 확인, 필요한 독립 검수 요청 | 자체/독립/렌더링 상태와 미실시 항목 |
| 최종 확정 | 출원용 특정 파일 승인 | 대상 파일·버전·해시·승인 범위 |

이미 지시한 창작 범위 안의 구체화·수학식 창작마다 승인을 요구하지 않는다. 사람의 행위는 실제로 입력·선택·검토가 필요할 때 표시한다.
‘확인 필요’ 요청에는 선택하거나 답해야 할 사항과 영향을 명시하고, 의미 없는 일괄 ‘다음 단계 승인’ 버튼을 두지 않는다.

## 8단계 진행 표시

| 하네스 stage | 화면 이름 | 확인할 자료 |
|---|---|---|
| intake | 자료 접수 | 사건 식별, 입력 목록, 원본 해시 |
| analysis | 발명 자료 정리 | 목적·문제·구성·누락·제약 |
| concretization | 발명 구체화 | 방향, 구성 또는 동작, 자료·창작 이력 |
| points | 특허 포인트 | 문제·수단·작동 관계·기대 효과 |
| claims | 독립항·종속항 | 청구항 원문, 의존관계, 포인트 연결 |
| drafting | 본문·도면 작성 | 명세서, 도면, 대응표 |
| review | 내용·문서 검수 | 자체·독립·렌더링 검수 구분 |
| final | 출원용 문서 확정 | 특정 버전 승인, 현재 파일 해시 일치 |

메이킹에서는 concretization을 ‘창작·구체화’, points를 ‘특허 포인트 창작’으로 표시한다.
준비 6단계는 진행표 위의 별도 트래커로 두고, 작성 8단계의 stage 값은 유지한다. 준비 완료 후에도 준비 근거와 설정 경로를 펼쳐 볼 수 있다.
`final`은 문서 확정이며 실제 출원 접수 완료를 뜻하지 않는다. 출원 접수는 별도 사건 업무 상태로 표시한다.

현재 stage 이전의 모든 단계를 자동 완료 처리하지 않는다. 현 스키마에는 단계별 완료 이력이 없으므로 근거가 있는 단계만 완료로 표시한다.
stage/status, 검수보고서, 실행기록을 구분해 보여주고 확인되지 않은 과거 단계는 ‘완료 기록 없음’으로 표시한다.
총 진행률을 임의 계산하지 않는다. 초기에는 ‘현재 4/8 · 특허 포인트 창작’처럼 현재 위치만 보여준다.

## 메이킹 전용 상세

### 동작·데이터

각 동작의 입력(최대 3개), 처리, 출력(최대 2개), 기능을 순서대로 보여준다.
동일 데이터 ID를 기준으로 앞 출력과 뒤 입력을 연결하고 선택 시 명칭·형식·단위·시간 기준·생성자·소비자를 표시한다.
코드 검사 결과는 초과 입력/출력, 정의 누락, 생성 전 사용, 연결 불일치, 미사용 데이터로 분류한다.
분기·반복은 실제 의미 검수 여부를 함께 표시한다. ID가 맞는 것만으로 의미 일치를 검수 완료로 판단하지 않는다.
장치·조성물에 방법 동작이 없으면 ‘동작 흐름 해당 없음’과 구성요소 중심 보기를 제공한다.

### 특허 포인트·청구항

포인트별 문제 → 기술적 수단 → 기대 효과 → 대상 구성/동작 → 청구항 번호를 표시한다.
구성의 출처 성격은 제공 자료 / 분석적 추론 / 창작, 사용자 확인 상태는 별도 배지로 표시한다.
미확정 창작이라는 이유만으로 오류 배지를 붙이지 않는다. 근거 경로 누락이나 사용자 제외 구성 사용을 구분한다.
수학식의 본문 기재와 종속항 수학식 검사를 별도로 표시한다.
청구항을 선택하면 종속관계와 포인트가 보이며, 자동 수학식 검사의 한계 및 실제 문서 대조 상태를 표시한다.

### 산출물과 검수

파일 상태는 미작성 / 파일 확인 / 검수 미실시 / 검수 완료 / 변경 후 재검토로 구분한다.
파일 존재만으로 단계를 완료 처리하지 않는다. 본문·도면·수식·문서 렌더링 검수는 각각 근거를 표시한다.
승인 해시가 현재 파일과 다르면 이전 승인은 이력으로 보존하고 현재 버전에 ‘재검토 필요’를 표시한다.
운영 검사기 버전·검사 시각·입력 해시를 함께 보관하여 오래된 결과와 현재 결과를 구분한다.

## 기존 사건 표시와 식별

case.yaml이 있는 사건은 스키마를 검증한 뒤 stage/status를 읽는다.
case.yaml이 없는 기존 사건도 폴더명으로 목록에 표시하되 ‘하네스 상태 미연결’로 둔다.
읽을 수 없는 파일, 잘못된 JSON, 알 수 없는 버전은 ‘자료 확인 필요’로 표시하고 다른 사건 조회는 계속한다.
폴더명에서 추출한 번호는 후보에 불과하며 확정 case_id로 사용하지 않는다.
복수 사건번호가 있는 폴더는 하나의 프로젝트에 여러 사건 후보가 있는 상태로 표시한다. 번호를 임의로 하나 선택하거나 별도 사건을 병합하지 않는다.
확인된 프로젝트↔사건 연결은 로컬 DB의 별도 연결 기록으로 보관할 수 있으나 사용자 확정 전에 자동 생성하지 않는다.
기존 폴더에 case.yaml·STATUS.md·새 AGENTS.md를 만들거나 기존 파일을 정규화하지 않는다.

## 데이터 원본과 동기화

| 데이터 | 원본 | 대시보드 처리 |
|---|---|---|
| 작성 단계·상태·방향 | case.yaml | 읽기 전용 투영 |
| 동작·자료창작·청구항 | operations/evidence/claims.json | 검증 후 표시 |
| 사용자 확정 이유 | DECISIONS.md, approvals | 원문 및 대상 버전 연결 |
| 상태 요약 | STATUS.md | 참고 표시, case.yaml보다 우선하지 않음 |
| 수행자·내부기일·업무 상태 | 기존 업무 DB의 확인값 | 확인된 전체 사건번호로 연결 |
| 웹 조회·검사 이력 | 신규 로컬 DB 기록 | 파일 해시·검사기 버전 포함 |
| 시작 준비·사람 확인 | 신규 로컬 DB의 onboarding 기록 | 준비 단계·행위자·시각·증거·관련 입력 버전 |

업무 DB의 출원 업무 단계와 하네스의 작성 단계는 별도 항목이다. 한쪽을 읽고 다른 쪽을 자동 덮어쓰지 않는다.
쓰기 없이 현재 파일을 읽고, UI용 조회 캐시·검사 결과만 DB에 보관한다.
시작 준비 기록은 작성 stage와 별도로 보관한다. proposed schema: project_id(생성 전에는 setup_id), step_key, status, actor, confirmed_at, evidence_type, evidence_ref, input_fingerprint.
상태는 대기 / 사람 작업 필요 / 점검 대기 / 확인됨 / 재확인 필요로 구분한다. 사용자 확인과 자동 점검의 근거 종류를 합치지 않는다.
웹에서 준비 체크를 저장해도 기존 개별 사건의 case.yaml·STATUS.md·AGENTS.md는 수정하지 않는다.
신규 초기화 요청에서 승인된 새 폴더 생성과 초기 메타데이터 기록만 예외다. Codex의 실제 사건 작업은 그 사건에서 사용자가 지시한 범위에 따른다.
프로젝트명·사건번호·샘플 버전이 바뀌면 관련 dry-run과 이후 준비 확인을 재검토한다. 생성 후에는 이름을 자동 변경하지 않는다.
동일 파일시스템에 폴더가 있다는 것과 그 폴더가 Codex의 기본 작업 폴더라는 것은 별개의 사실이다.
대시보드에서 stage/status를 직접 바꾸는 기능은 1차 범위에서 제외한다. 나중에 도입하면 파일과 DB의 동시 변경·충돌 정책부터 설계한다.
업무 DB의 사용자 확정값을 새 파일 추정값으로 덮어쓰지 않는다. 새 자동 판단을 사용자에게 제안할 때는 decision_run/decision_item 및 스냅샷을 연결한다.
기존 확정값의 단순 조회와 새로운 상태 추정은 구분한다.

## API와 구현 경계

조회 API 제안:
- GET `/api/specifications/summary`
- GET `/api/specifications/projects`
- GET `/api/specifications/projects/:id`
- GET `/api/specifications/projects/:id/checks` (마지막 검사와 현재 입력의 일치 여부)
- GET `/api/specifications/setups/:id` (폴더 생성 전·후의 준비 절차와 확인 근거)

사용자 조작 API 제안:
- POST `/api/specifications/projects/:id/check` — 고정 검사기를 읽기 전용으로 실행, 결과는 DB에 보관
- POST `/api/specifications/init/preview` — 새 프로젝트 생성 dry-run
- POST `/api/specifications/init` — 동일 입력·샘플 해시의 검증 결과로 신규 폴더만 생성
- POST `/api/specifications/setups` — 신규 시작 입력과 준비 기록 생성(DB만)
- POST `/api/specifications/setups/:id/confirm` — 사람의 설정·자료 투입 확인을 불변 이벤트로 기록(DB만)
- POST `/api/specifications/setups/:id/verify` — 파일 구조·메타데이터·읽기 가능한 접수 기록의 실제 근거 확인(사건 파일 쓰기 없음)

verify는 웹 서버에서 확인한 파일 접근을 Codex 접근 확인으로 가장하지 않는다. 실제 작업의 경로·공통 자료 읽기 기록이 없으면 사용자 확인 상태로만 둔다.
수동 복사 프로젝트를 시작 준비 기록에 연결할 때도 고정 루트의 기존 폴더를 읽기만 하며 폴더나 파일을 재생성하지 않는다.

프로젝트 ID는 서버가 발급한 불투명 ID로 사용한다. 사용자가 보내는 절대경로나 폴더명을 파일 읽기 경로로 직접 사용하지 않는다.
고정 루트·realpath·junction/symlink·상대 경로·파일 크기·시간 제한을 검증한다. 관련 구조화 파일만 읽고 원본 문서 전체를 목록 조회 때 파싱하지 않는다.
검사기는 고정 Python 실행 파일과 고정 harness.py에 인자 배열로 전달하여 shell 없이 실행한다.
로컬 요청·Origin 검증 및 중복 요청 방지는 기존 API 정책을 재사용한다. 초기화는 샘플 해시 변경·동일 폴더 동시 생성·기존 폴더를 거부한다.
임의 명령 실행, 브라우저의 직접 파일 쓰기, 자동 출원·메일 전송 기능은 포함하지 않는다.

- `dashboard/app/specifications/page.tsx`: 신규 화면

## 구축 순서와 완료조건

1. 읽기 전용 연결: 홈 카드, 목록·상세, 준비 6단계 안내·경로 복사·첫 요청문, 작성 8단계, 기존 사건 미연결 표시.
2. 메이킹 상세: 동작·데이터, 포인트·청구항, 자료·창작 구분과 검사 결과.
3. 신규 초기화: 미리보기→생성, 준비 단계 사람 확인·근거 기록, 검사 결과 저장, 확인된 업무관리 연결.

필수 회귀 사례:
- 하네스가 있는 합성 사건의 정확한 표시, 없는 사건의 비추정 표시, 복수 번호와 전체 접미사 보존
- 목록/상세/재조회/검사 전후의 기존 사건 파일 해시 불변
- 입력·출력 제한·dangling·종속항 수학식 및 오래된 검사 결과 표시
- 파일 존재와 검수 완료, 문서 확정과 출원 접수 완료 구분
- malformed JSON·크기 초과·부재·접근 오류의 사건별 격리
- 경로 탈출·junction·잘못된 Origin·동시 초기화 거부, dry-run 무변경
- 자동/수동 복사 경로 모두 올바른 샘플 구조·사건 식별·샘플 해제를 확인하며, 잘못 중첩된 샘플 폴더 감지
- Codex 기본 폴더와 보조 폴더의 안내 경로 일치, 사용자 설정 체크만으로 자동 접근 확인을 완료하지 않음
- README만 있는 원본 폴더를 자료 투입 완료로 판정하지 않음
- 경로/입력/샘플 변경 뒤의 준비 확인 무효화, 중복 체크 요청의 멱등성, 행위자·시각 보존
- 준비 완료는 intake 시작이며, 작성·문서 승인·출원 접수 완료로 승격하지 않음
- 좁은 화면의 목록/상세 전환 및 키보드 조작
