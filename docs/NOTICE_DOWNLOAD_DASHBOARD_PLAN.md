# 통지서 자동 다운로드 대시보드 기획

작성: 2026-09-21. 상태: **원장·로컬 API·`/downloads` 화면·OA 프로젝트 안전 생성 구현 완료, 예약 감지·자동 게시 비활성**.

이 문서는 의견제출통지서, 거절결정서, 우선심사신청보완요구서 자동 다운로드의 감지부터 ZIP 게시까지를 로컬 웹 대시보드에서 확인하는 방법을 정의한다. 메일 감지·다운로드 조건은 [Outlook 통지 메일 자동 다운로드 트리거 기획](./OUTLOOK_NOTICE_AUTO_TRIGGER_PLAN.md), 문서별 파일 선택과 검증은 [OA·거절결정 다운로드 기획](./OA_DOWNLOAD_PLAN.md) 및 [우선심사신청보완요구서 다운로드 기획](./PRIORITY_EXAM_SUPPLEMENT_DOWNLOAD_PLAN.md)을 따른다.

## 1. 화면 위치와 목적

대시보드 상단 탐색에 `문서 자동수집`을 추가하고 전용 경로를 `/downloads`로 둔다. 이 화면은 자동 실행의 운영 상태와 파일 처리 이력을 보여 준다. 메일·EasyPAT 근거가 모호해 사용자의 판단이 필요한 항목은 기존 `/analysis`의 검토 항목으로 연결한다.

화면에서 바로 확인할 수 있어야 하는 질문은 다음과 같다.

- 오늘 예약 작업이 실행됐는가, 다음 실행은 언제인가.
- 어느 메일부터 다시 감지하며 현재 어디까지 읽었는가.
- 어떤 사건의 어떤 통지서가 발견됐고 지금 어느 단계인가.
- 첨부 몇 개 중 몇 개가 검증됐는가.
- 완성된 ZIP의 이름과 게시 시각은 무엇인가.
- 보류·실패한 이유와 다음 재개 지점은 어디인가.
- 같은 통지의 두 메일이 하나의 작업으로 합쳐졌는가.

## 2. 화면 구성

### 예약 실행 상태

화면 상단에 다음 값을 한 줄로 표시한다.

- 자동 실행 상태: 비활성, 관찰, 종류별 제한 활성, 전체 활성
- 기본 실행 시각과 시간대: 매일 오전 9시 `Asia/Seoul`
- 다음 예정 시각, 마지막 실제 시작·종료 시각
- 마지막 실행 결과: 완료, 일부 완료, 실패, Outlook 사용 불가
- `recoveryFrom`과 `scanTo`
- Outlook·EasyPAT의 마지막 확인 상태와 확인 시각

예약을 놓친 뒤 로그인하여 실행한 경우에는 `예약 09:00 · 실제 시작 10:24`처럼 두 시각을 함께 보여 준다. 이 패널의 새로고침은 로컬 DB만 읽으며 Outlook 감지나 EasyPAT 요청을 시작하지 않는다.

### 요약 카드

현재 실행 또는 오늘 실행을 기준으로 다음 수를 표시한다.

- 감지 메일 수와 통지 후보 수
- 처리 중인 통지 수
- 확인 필요 수
- 실패 수
- 오늘 게시 완료 수
- 중복으로 병합한 메일 수

메일 수와 통지 수를 분리한다. 업무요청 메일과 담당자 지정 메일 두 통이 통지 하나로 병합된 경우 `메일 2 · 통지 1 · ZIP 1`로 보이게 한다.

### 작업 목록

기본 정렬은 처리 중 → 확인 필요·실패 → 대기 → 최근 완료 순이다. 목록 열은 다음과 같다.

| 열 | 표시 내용 |
|---|---|
| 사건 | 전체 당소관리번호와 사건 상세 링크 |
| 문서 | 의견제출통지서 `nOA`, 거절결정 `n차`, 우선심사 보완 `n차` |
| 날짜 | 통지일과 마감기일 |
| 메일 | 연결된 업무요청·담당자 지정 메일 수와 직접 To 확인 여부 |
| 진행 | 현재 단계와 첨부 `검증 수/전체 수` |
| 결과 | 예상 또는 실제 ZIP 이름 |
| 상태 | 대기, 처리 중, 확인 필요, 실패, 완료, 중복 병합 |
| 갱신 | 마지막 상태 변경 시각 |

문서 종류, 상태, 통지일 범위로 필터링하고 전체 당소관리번호의 정확·부분 검색을 제공한다. 기본 화면은 최근 30일과 미완료 전체를 조회하며 과거 완료 이력은 페이지 단위로 불러온다.

### 실행 이력

일일 실행별로 예약 시각, 실제 시작·종료, `recoveryFrom`, `scanTo`, 발견 메일, 새 통지, 재개 작업, 게시 완료, 보류·실패 수를 표시한다. 중단된 실행에는 마지막 안전 단계가 보인다. 한 통지가 여러 일자 실행에 걸쳐 처리되면 각 실행의 시도 번호와 결과를 모두 남긴다.

### 통지 상세

목록 행을 열면 다음 내용을 시간순으로 표시한다.

1. 연결 메일: 제목, 수신시각, 역할, 직접 To 판정 결과. 본문 전체와 연락처는 기본 노출하지 않는다.
2. EasyPAT 근거: 전체 당소관리번호, 문서 종류, 진행번호, 통지일·기일, 첨부 스냅샷 버전.
3. 첨부: 원본 파일명, 문서명, 크기, 목록·다운로드·검증 상태. 해시는 앞 12자만 기본 표시하고 상세에서 전체값을 복사할 수 있게 한다.
4. 작업 시도: 시도 번호, 시작·종료 시각, 단계, 처리 파일 수, 마지막 안전 단계, 오류 코드.
5. 게시 결과: 최종 ZIP 이름, 항목 수, 크기, SHA-256, 게시 시각. 목적지 경로는 고정 intake 별칭과 파일명으로 표시한다.
6. 중복 근거: 기존 통지키와 패키지에 연결된 메일, 새 작업을 만들지 않은 이유.

### 대응 프로젝트

게시 완료 통지에는 대응 프로젝트의 미생성·생성 점검·폴더 생성·Codex 연결 필요·접수 작업 필요·진행 중·사용자 대기·대응 완료 상태를 별도로 표시한다. 프로젝트가 없으면 고정 중간사건 루트 아래 예상 폴더와 가져올 ZIP을 미리 보여 주고, 사용자가 의뢰인식별명과 프로젝트명을 확인한 뒤에만 생성 dry-run을 시작한다.

폴더 생성 뒤에는 권장 Codex 작업 제목과 복사 가능한 접수 명령을 표시한다. 프로젝트 진행 단계와 사용자 행동 요약은 다운로드 상태와 분리한다. 상세 구조와 종류별 순서도는 [통지 종류별 대응 프로젝트 생성·진행 기획](./NOTICE_RESPONSE_PROJECT_WORKFLOW.md)을 따른다.

## 3. 단계와 진행률 표시

진행 표시는 DB에 커밋된 단계와 파일 수만 사용한다. 경과 시간으로 추정한 백분율은 표시하지 않는다.

| 내부 단계 | 화면 표시 | 진행 정보 |
|---|---|---|
| 메일 후보 기록 | 메일 감지 | 감지 메일 수 |
| 직접 To·템플릿 통과 | 수신 조건 확인 | 연결 메일 역할 |
| EasyPAT 진행행 확정 | 원본 확인 | 진행번호·통지일·기일 |
| 첨부 스냅샷 확정 | 첨부 확인 | 전체 첨부 수 |
| `download_job.queued` | 다운로드 대기 | 예약·시도 번호 |
| `download_job.running` | 파일 다운로드 | 완료 파일 수/전체 파일 수 |
| `download_job.staged` | ZIP 생성 완료 | ZIP 항목 수 |
| `download_job.verified` | ZIP 검증 완료 | 크기·해시 확인 |
| `download_job.published` | 게시 완료 | 파일명·게시 시각 |
| `held` | 확인 필요 | 보류 코드와 필요한 조치 |
| `failed` | 실패 | 실패 단계·오류 코드·재개 가능 여부 |

완료 표시는 `download_package`가 있고 목적지 파일의 이름·크기·SHA-256이 원장과 일치할 때만 사용한다. ZIP이 존재하지만 DB 완료 기록이 빠진 복구 상태는 `게시 확인 중`으로 표시한다. `duplicate`는 별도 패키지 상태로 저장하지 않고 기존 완료 통지와의 병합 결과로 표시한다.

화면은 처리 중 작업이 있을 때만 5초 간격으로 로컬 조회 API를 갱신한다. 처리 중 작업이 없으면 60초 간격 또는 사용자의 새로고침으로 갱신한다. 이 조회는 자동 다운로드 실행 주기와 무관하며 외부 네트워크 요청을 발생시키지 않는다.

## 4. 데이터 원장 보강

현재 `009_notice_download_ledger.sql`의 `notice`, `notice_mail_link`, `notice_attachment`, `download_job`, `download_package`를 유지하고 다음 마이그레이션에서 실행·단계 원장을 추가한다.

- `notice_detection_run`: 예약 시각, 실제 시작·종료, `recovery_from`, `scan_to`, 상태, 마지막 안전 단계, 시도 번호와 집계
- `notice_run_item`: 일일 실행과 통지·다운로드 작업의 연결, 해당 실행의 결과와 중복 병합 여부
- `notice_pipeline_event`: 통지, 작업, 실행, 단계, 파일 처리 수, 상태, 오류 코드, 발생 시각을 기록하는 추가 전용 이력
- `notice_operator_request`: 다시 검증·재개 요청, 요청 당시 행 버전·입력 해시, 처리 상태와 처리 실행
- `notice_project_link`·`notice_project_stage`·`notice_project_event`: 통지와 사건 프로젝트 연결, 현재 단계·사용자 행위, 생성·승인·제출 이력

같은 단계 이벤트가 다시 들어와도 중복 생성되지 않도록 `실행 + 통지 + 작업 + 단계 + 시도 + 순번`에 멱등 키를 둔다. 목록 API는 이벤트를 매번 조합하지 않고 검증된 현재 투영을 사용하고, 상세 화면에서만 전체 이벤트 이력을 읽는다.

현재 `notice.notice_kind`는 의견제출통지서와 거절결정서만 허용한다. 우선심사 보완을 구현할 때 `priority_exam_supplement_request`를 허용하도록 SQLite 테이블 재작성 마이그레이션과 기존 행 수·외래키 무결성 검사를 함께 수행한다. 기존 완료 원장과 패키지 버전은 보존한다.

## 5. 로컬 API 계약

읽기 API는 다음과 같이 나눈다.

- `GET /api/downloads/summary`: 활성화 상태, 다음 예약, 마지막 실행과 오늘 집계
- `GET /api/downloads/runs`: 일일 실행 이력
- `GET /api/downloads/notices`: 필터·검색·페이지가 적용된 작업 목록
- `GET /api/downloads/notices/:id`: 메일, EasyPAT 근거, 첨부, 작업 시도와 패키지 상세
- `GET /api/downloads/jobs/:id/events`: 한 작업의 단계 이벤트
- `POST /api/downloads/notices/:id/recheck-requests`: 허용된 보류 건의 새 검증 요청 기록
- `POST /api/downloads/jobs/:id/resume-requests`: 재개 가능한 실패 작업의 재개 요청 기록
- `POST /api/downloads/notices/:id/project-previews`: 고정 루트의 예상 폴더·패키지·중복을 읽기 전용 검증
- `POST /api/downloads/notices/:id/projects`: 유효한 preview 토큰으로 사건 프로젝트 생성

화면에서 사용자가 실행할 수 있는 복구 동작은 `다시 검증`과 `재개 요청`으로 제한한다. 두 요청은 브라우저 프로세스가 직접 EasyPAT이나 파일 시스템을 다루지 않고 원장에 명령을 기록하며, 로컬 작업자가 다음 실행에서 낙관적 잠금과 현재 입력 해시를 확인한 뒤 처리한다. 완료 패키지 재생성, 기존 파일 덮어쓰기와 임의 경로 지정은 제공하지 않는다. 게시 완료 OA에는 프로젝트 생성 preview와 유효한 preview 토큰을 사용한 create를 제공한다.

모든 API는 `127.0.0.1` 요청만 허용한다. 응답에는 쿠키, SQL, EasyPAT 내부키·업로드 경로, Outlook EntryID 원문과 메일 본문 전체를 포함하지 않는다. 오류 메시지는 사용자용 설명과 안정적인 오류 코드를 분리한다.

## 6. 사용자 알림과 보류 처리

대시보드 탐색 메뉴에는 `확인 필요 + 실패` 수만 배지로 표시한다. 완료 건은 화면 안의 오늘 집계와 이력에 표시하고 외부 알림을 반복하지 않는다.

보류 상세에는 다음 세 항목을 함께 보여 준다.

- 이유: 예를 들어 `기일 불일치`, `첨부 묶음 복수`, `목적지 동명 충돌`
- 자동 재확인 조건: 새 짝 메일, 첨부 목록 변경, 다음 일자 실행 등
- 사용자 조치: `/analysis`에서 근거 확인, 파일 충돌 정리, EasyPAT 세션 확인 등

입력 해시가 같은 결정적 보류는 매일 새 실패처럼 누적하지 않는다. 마지막 확인 시각만 갱신하고 보류 시작 시각과 최초 원인은 유지한다.

## 7. 구현 순서

1. **원장 마이그레이션:** 실행·이벤트·요청·프로젝트 연결 테이블과 우선심사 보완 종류를 추가하고 기존 `009` 데이터 보존을 검증한다.
2. **읽기 서비스:** 목록 투영, 상태 매핑, 집계, 페이지 처리와 민감정보 제거를 구현한다.
3. **읽기 전용 화면:** `/downloads`의 예약 상태, 카드, 작업 목록, 실행 이력과 상세를 구현한다.
4. **실행기 연결:** Outlook 감지기와 다운로드 작업자가 트랜잭션 안에서 실행·단계 이벤트를 기록하게 한다.
5. **재개 요청:** 허용된 상태에서만 다시 검증·재개 요청을 기록하고 중복 요청을 차단한다.
6. **프로젝트 연결:** 게시 완료 건의 프로젝트 생성 preview, 사용자 확인, 안전 초기화와 단계 표시를 구현한다.
7. **운영 활성화:** 복구 범위 dry-run과 종류별 실제 단건 게시 검증 후 의견제출통지서부터 기능 플래그를 켠다.

화면을 먼저 읽기 전용으로 완성해 현재 원장과 P261252 완료 패키지가 정확히 보이는지 확인한 뒤 실행기 쓰기를 연결한다.

## 8. 검수 기준

- P261252 1OA 완료 건이 ZIP 하나, 완료 작업 하나와 정확한 첨부 수·한글 파일명으로 표시된다.
- 같은 통지의 두 메일은 메일 2건, 통지 1건, 패키지 1건으로 표시된다.
- OA·거절결정·우선심사 보완의 차수와 파일명 규칙이 서로 섞이지 않는다.
- 파일 다운로드 중 종료 후 재개하면 기존 파일 검증 수와 새 시도가 구분되고 ZIP이 중복 생성되지 않는다.
- Outlook 사용 불가, EasyPAT 세션 필요, 기일 불일치, 첨부 변경, 동명 충돌이 서로 다른 보류·실패 코드로 표시된다.
- 놓친 예약 실행은 예약 시각, 실제 시작 시각과 보존된 `recoveryFrom`을 함께 표시한다.
- 활성 작업이 없는 화면 조회는 Outlook·EasyPAT·intake 폴더를 변경하지 않는다.
- 목록 1,000건에서도 페이지 조회를 사용하고 민감정보가 API 응답과 브라우저 로그에 노출되지 않는다.
- `/downloads`와 다섯 읽기 API, 기존 필수 화면·API, dashboard lint·phase 테스트·build가 모두 성공한다.
- 다운로드 완료와 대응 프로젝트 완료가 별도 상태로 표시되고, 사용자 행위가 필요한 단계에는 다음 동작이 한 문장으로 제시된다.
