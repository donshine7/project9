# LLM Wiki 구조와 3단계 실행 계획

## 원칙

Wiki는 원본 DB를 대체하는 장문 문서가 아니라, 검증된 사실과 근거를 사람이 읽기 좋게 보여주는 파생 화면이다. SQLite가 상태·관계·이력의 원본이며 LLM은 초안을 제안한다. 별도 OpenAI API 키나 상시 실행 LLM 서버 없이 현재 Codex 프로젝트에서 모델별 작업을 수행한다. 웹의 메일 수집 버튼은 Outlook 수집만 수행하고 LLM 분석을 실행한 것처럼 표시하지 않는다.

## 정보 계층

| 계층 | 저장 단위 | 변경 원칙 |
|---|---|---|
| 원본 증거 | mail_item, 원본 ID·본문 해시·발신/수신·시각 | 원문 보존, 인용 위치 검증 |
| 관찰·판단 | input_snapshot → decision_run → decision_item → decision_evidence | 실행 당시 입력과 필드별 후보 보존 |
| 검토·확정 | user_feedback + event | 수락/수정/반려를 원자적으로 기록 |
| 구조화된 업무 | matter, work_item, assignment, action_item, 관계 테이블 | 확정값은 AI가 덮어쓰지 않음 |
| 날짜별 지식 | knowledge_entry | 한 사실/대상/날짜/근거, 사용자 비고와 분리 |
| 읽기용 Wiki | 대상별 버전·단락·근거 이벤트 연결 (4단계) | 이전 버전 유지, 변경분으로 새 버전 생성 |

## Wiki 페이지 4종 + 업무 하위 블록

- 사건: 전체 당소관리번호를 제목으로 사용. 사무소·국가·관계, 업무종류별 현재 상태, 서비스 종류, 담당자1/2·DB·수임자, 비용 조건, 본인/팀원 Action, 날짜별 연락·결정, 쟁점·미확정 사항, 근거와 개정 이력.
- 회사: 내부 organization ID를 키로 하고 회사명은 수정 가능한 표시값. 개인사업자·법인·미정의 회사 구분, 연결 사건·자연인, 비용/연락 선호 등 회사 차원의 확정 사실, 회사에 직접 관련된 날짜별 기록. 사건별 기술 상세는 링크로 연결한다.
- 자연인: 내부 person ID, 이메일은 동일인 추정의 근거일 뿐 불변 식별자로 삼지 않는다. 소속과 역할, 관련 회사·사건, 직접 요청·약속·연락 변경. 이름이 같다는 이유로 자동 병합하지 않는다.
- 그룹: GPxxxxxx 또는 GPPxxxxxx 등 대표 사건번호 전체를 포함하는 별도 ID. 대표 사건, 다대다 구성원, 공동 목표·공유 일정·공통 기록. P와 PP 혼합 및 중복 그룹을 허용하고 동일 계열/우선권 관계를 그룹과 혼동하지 않는다.
- 사용자 수락이 끝난 회사·사람 관계는 새 관계를 추론하지 않고 기존 수락 이벤트와 원본 메일 인용을 대상별 `wiki_entry` 날짜 기록으로 파생할 수 있다. 같은 후보의 반복 반영은 차단한다.
- 업무는 별도 work_item ID를 사용한다. 출원/중간사건/등록 등 업무종류, 업무단계, 현재상태를 분리한다. 일반출원·기획·메이킹 등 서비스는 별도 필드다. -PRO#만으로 기획 서비스를 부여하지 않는다.

각 페이지에는 `사용자 비고`, `확정된 현재 정보`, `날짜별 중요내용`, `검토 대기`를 별도 구역으로 둔다. 날짜 기록을 수락했다고 법적 상태 전체가 확정되는 것은 아니다. “등록결정 안내 메일 수신”과 “등록완료”는 다른 사실이다.

## 날짜별 기록의 구체적 구조

원자 기록: id, entity_type/id, entry_date(Asia/Seoul), content, candidate_id, event_id, source_mail_ids, created_at. 4단계에서 event_type, occurred_at 정밀도, 관련 대상 링크, supersedes_entry_id를 추가하여 수정·취소된 사실을 추적한다.

- 메일 발신일과 실제 사건 발생일을 구분한다. 명시된 발생일이 없으면 메일의 한국 날짜로 표시한다.
- 한 사건의 메일을 연결 회사·사람·그룹에 무조건 복사하지 않는다. 각 대상에 직접 관련된 문장만 후보로 분해하고 공통 근거를 링크한다.
- 원본 메일의 인용문·메일 ID·필드 위치·해시를 보존한다. 첨부파일은 아직 읽지 않았다면 내용 확인을 주장하지 않는다.
- 반복 안내/회신은 새 사실만 추가한다. 동일 문구 제거만으로 다른 날짜의 실제 반복 요청을 삭제하지 않는다.
- 상충하는 사실은 최신 메일만 보고 덮어쓰지 않고 충돌로 보낸다. 사용자 확정값은 보호하고 외부 원본은 EasyPAT 정확 일치 조회 > 사건등록 완료 메일 > Excel > 일반 메일 추정 순서를 따른다. EasyPAT와 사용자 확정값의 충돌도 자동 변경하지 않고 검토로 보낸다.
- 원문이 없어지거나 변경되면 스냅샷 검증에서 차단한다. 추후 삭제/보존 정책은 별도로 승인받는다.

## 3단계 구현 범위

1. `config/analysis-contract.md`에 역할별 JSON 출력 계약을 정의한다.
2. CLI에서 분석 실행을 준비한다. 원문은 중복 복제하지 않고 내용 해시를 고정하며, 당시 구조화 정보·업무·Action·담당자·메일 연결·이전 후보를 동결한다.
3. 주 작업이 config 라우팅의 모델/추론을 명시하여 전문 에이전트를 시작한다. 실제 작업 식별자를 bind하기 전에는 결과를 반영할 수 없다. 예정 모델은 실제 모델로 표시하지 않는다.
4. 반환 결과를 필드별로 검증한다: 입력 메일 전체 coverage, 역할·필드 제한, 정확한 인용, 기존 사건 식별자, 날짜 유효성, 신뢰도, 결과 재수입 멱등성.
5. `analysis_candidate`와 기존 판단 원장을 하나의 트랜잭션으로 기록한다. 새 회사/사람/그룹, 업무 상태 변경, Action 자동 완료는 수행하지 않는다.
6. 기한/비용/출원/제출/등록 등의 후보와 사건 연결은 고위험으로 올린다. 별도 risk_verifier Sol/high 결과가 전부 confirmed인 경우에만 수락 가능하다. 수정된 고위험 값에는 기존 검증을 재사용하지 않는다.
7. `/analysis`에서 근거·신뢰도·실제 모델·프롬프트 버전을 확인하고 수락/수정/반려한다. 수락한 Action은 장진태 관리 화면에 생성된다. 사실 요약 수락은 knowledge_entry에 기록하되 기존 사용자 비고를 변경하지 않는다.
8. 검토와 업무 반영, 필드별 user_feedback/event/comparison은 함께 커밋한다. 미검토를 정답으로 세지 않으며 자유문 수정은 자동 오류/학습 사례로 확정하지 않는다.

3단계의 사실 추출은 메일 단위 요약을 저장한다. 사건·회사·사람·그룹에 맞춘 확정 요약 투영과 Wiki 버전 UI는 4단계다. 세부 회사/사람 자동 식별·병합, 첨부 Excel 분석, 법정기일 계산은 아직 제공하지 않는다.

## 실행 명령 (dashboard 디렉터리)

`npm run analysis -- mails`: 기존 DB 메일 ID 조회. Outlook을 다시 읽지 않는다.

`npm run analysis -- prepare mail_fact_extraction MAIL_ID...`: 실행/입력 동결. `matter_linking`, `action_judgement`, `high_risk_verification`도 같은 형태다.

`npm run analysis -- packet RUN_ID`: 전문 에이전트 입력. 원문이 들어 있으므로 출력 파일이 필요하면 Git 제외 `.analysis-private` 또는 운영 DB 영역만 사용한다.

`npm run analysis -- bind RUN_ID AGENT_ID MODEL EFFORT`: 실제 하위 작업 시작 후 주 작업이 디스패치 메타데이터 기록.

`npm run analysis -- ingest JSON_PATH`: 주 작업이 스키마·근거 검증 후 후보 저장. 실패하면 전체 롤백, 같은 결과 재시도는 멱등, 다른 결과 덮어쓰기 금지.

`npm run analysis -- fail RUN_ID ERROR_CODE`: 실패/중단 기록. 재실행은 새 스냅샷과 새 실행으로 남긴다. LLM 사용 불가 시 자동 모델 대체 없음.

모든 DB 조작 명령은 npm 실행 디렉터리가 dashboard여야 한다. 테스트는 임시 DB만 사용한다. 운영 DB는 적용 전에 백업한다. 웹은 후보 조회/검토만 제공하며 모델 실행이력을 위조할 수 있는 ingest/bind API를 노출하지 않는다.

## 4단계 구현 순서 (구현 결과는 PHASE4_VERIFICATION.md)

1. 메일 단위 확정 관찰을 대상별 원자 사실로 분해·연결. 업무 상태/관계 충돌 해결 UX와 누락 추가 비교를 확장.
2. wiki_revision의 사건 전용 레거시 구조를 일반 대상용 revision/section/evidence 구조로 마이그레이션. 문장별 evidence_event_ids 필수.
3. wiki_synthesizer Terra/medium은 검증된 이벤트만 읽고 현재 상태·날짜별 변경·미해결 사항의 개정안을 반환.
4. 주 작업이 근거와 현재 entity version을 검증하고 새 Wiki 버전으로 게시. 과거 버전은 변경하지 않음.
5. 사건·회사·사람·그룹 화면과 근거 탐색·변경 비교, 동기화/모델 실행 실패 재처리, 전체 메일 회귀·복원 검증.

3단계 검증용 표본 실행과 98건 전체 운영 분석은 별개로 표시한다. 표본 결과를 전체 처리 완료로 보고하지 않는다.

4단계에서는 `wiki_entry`, `wiki_draft`, `entity_wiki_revision`으로 구현했다. 레거시 `wiki_revision`은 삭제하지 않고 보존본으로 조회한다. 사용자 비고는 최신 DB 값으로 표시하며 AI 문장과 분리한다. 메일 기재 관찰과 사용자 확정 기록은 provenance로 구분하고, 전문 에이전트의 모든 문장에 이벤트 근거를 요구한다. 구체적 명령·테스트·운영 검증/남은 범위는 `PHASE4_VERIFICATION.md`에 기록한다.
