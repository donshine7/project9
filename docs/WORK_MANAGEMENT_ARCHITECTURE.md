# 당소관리번호 중심 업무관리 아키텍처

## 2026-09-22 Wiki 목표 설계 개정

사용자 결정에 따라 **SQLite는 업무 운영 원본, Obsidian Markdown은 Wiki 본문 원본**으로 전환한다. 현재 코드는 아직 SQLite 본문 저장 방식이다. 이후 구현의 기준은 [전체 작업 기획 v2](orchestration/WIKI_MARKDOWN_MASTER_PLAN_2026-09-22.md)와 [이관·복구·평가 계약](orchestration/WIKI_MARKDOWN_MIGRATION_AND_EVAL_2026-09-22.md)이다.

목표 구조에서 `entity_wiki_revision`은 활성 본문 저장 대신 버전·해시·근거·검토와 파일 이력 참조를 맡고, 대시보드는 Markdown을 읽는다. 문서 편집은 DB 업무 확정값을 자동 변경하지 않는다. 이전 본문은 Vault Git/백업으로 보존하며 기존 본문 컬럼 제거는 이관과 복구 검증 후 수행한다. 아래 SQLite Wiki 본문 관련 내용은 전환 전 구현의 설명으로 읽는다. 다른 업무 규칙은 유지한다.

## 1. 목표와 운영 원칙

이 시스템은 이메일 자체가 아니라 **당소관리번호**를 중심으로 사건, 회사, 자연인, 업무, Action과 지식 기록을 연결한다. 별도 OpenAI API 앱은 만들지 않는다. 장진태 님이 현재 Codex 프로젝트에 작업을 요청하면 Codex가 로컬 도구와 프로젝트 전용 에이전트를 조율하고, 로컬 대시보드와 데이터베이스가 결과를 보관한다.

핵심 원칙은 다음과 같다.

1. EasyPAT은 업무상 원본이며 연결된 읽기 전용 MCP의 정확 일치 조회로 확인한다. 조회할 수 없거나 제공되지 않는 필드는 출처와 신뢰도를 보관하고 차순위 근거로 판단한다.
2. 명시적 규칙으로 처리할 수 있는 일은 코드가 처리하고 LLM은 애매한 사실 판단에만 사용한다.
3. LLM은 변경 후보를 만들 뿐이다. 검증을 통과한 변경만 하나의 트랜잭션으로 DB에 반영한다.
4. 사용자 확정·수정값은 새 이메일 추정으로 자동 덮어쓰지 않는다.
5. 메일, 첨부파일, 운영 DB와 실행 기록은 사용자 PC에 둔다. 필요한 내용만 Codex 작업 문맥에 제공한다.
6. 장진태 님만 대시보드를 사용하며, 본인 Action과 팀원 Action을 함께 보고 대신 상태를 변경한다.

## 2. 시스템 경계

### 현재 유지하는 구성

- Outlook (classic) VBA의 신규 메일 자동분류
- `127.0.0.1:4173`에서 실행되는 로컬 대시보드
- 한국특허 가출원 프로젝트 초기화·진행 추적 기능
- 한국특허 명세서작성 프로젝트의 신규 준비 6단계와 작성 8단계 추적 기능
- 사용자가 Codex에 직접 작업을 요청하는 운영 방식
- 전체 당소관리번호 기반 EasyPAT 읽기 전용 MCP 서버와 7개 허용 도구

### 추가할 목표 구성

- 허용된 Outlook 폴더와 보낸 편지함의 읽기 전용 수집기
- 사건·업무·Action·Wiki를 저장하는 로컬 SQLite 데이터베이스
- 메일과 사건을 연결하는 결정적 파서 및 LLM 보조 분석
- 대시보드의 사건 상태·담당자·메모·Action 편집과 DB 반영
- 모든 자동 판단과 사용자 수정의 이력·근거 조회

대시보드는 외부 서버로 배포하지 않는다. 운영 DB의 권장 위치는 저장소 밖인 `%LOCALAPPDATA%\SSPAT\work-management\sspat-work.db`이며, WAL 모드와 정기 백업을 사용한다.

## 3. 입력 범위와 실행 트리거

### 메일 범위

- 받은 편지함과 허용된 하위 폴더를 읽는다.
- 보낸 편지함은 모두 읽는다.
- `대한변리사회` 계열 폴더, `결재`, `해외 출원 자동 안내`, `과제 자동 안내` 폴더는 읽지 않는다.
- 폴더 제외는 수집 시점에 적용한다. 제외 폴더의 본문을 읽은 뒤 버리는 방식은 사용하지 않는다.
- 읽기와 분석은 메일 이동·삭제·읽음 상태 변경과 분리한다.

### 실행 방식

사용자가 Codex에 요청해야 실행한다.

- `메일 업무 갱신해줘` → 기본 최근 1일
- `지난 일주일 갱신해줘` → 최근 7일
- `2026-09-01부터 2026-09-10까지 갱신해줘` → 지정 기간

향후 대시보드에 같은 세 선택지를 둘 수 있지만 버튼은 로컬 동기화 요청을 기록할 뿐, OpenAI API를 직접 호출하지 않는다. 예약 실행이 필요해질 때만 별도 Codex 예약 작업을 명시적으로 만든다.

## 4. 데이터 원본과 충돌 처리

필드마다 `source_type`, `source_id`, `observed_at`, `confidence`, `confirmed_by_user`를 보관한다. `config/source-priority.toml`이 출처 정책의 원본이며 기본 우선순위는 다음과 같다.

1. EasyPAT MCP의 전체 당소관리번호 정확 일치 조회
2. 사건등록 **완료** 메일
3. 업무 정리 Excel
4. 제목·본문에 명시된 일반 메일 정보와 메일 흐름 추정

장진태 님이 대시보드 또는 Codex 작업에서 확정한 값은 원본 순위와 별개의 `protected_override`로 취급한다. EasyPAT 값과 충돌해도 자동으로 덮어쓰지 않고 검토 항목을 만든다. 낮은 우선순위의 새 입력도 기존 값을 삭제하지 않고 새로운 관측값으로 쌓는다. 과거 실행에 기록된 우선순위 버전은 수정하지 않고 새 실행부터 `source-priority-v2`를 기록한다.

상태 테이블의 현재값은 `event`에서 투영한 값이다. 대시보드에서 상태를 바꾸면 기존 행을 조용히 덮어쓰지 않고 `user_status_changed` 이벤트를 추가한 뒤 현재 투영을 갱신한다.

모델 판단과 사용자 수정의 상세 구조, 비교 규칙, 품질 지표와 개선 승인 절차는 `docs/DECISION_FEEDBACK_DESIGN.md`를 기준으로 한다. 모델 판단은 필드별 `decision_item`으로 보존하며 사용자 수정은 이를 삭제하지 않고 별도 `user_feedback` 이벤트로 연결한다.

## 6. 사건번호와 업무 분류 규칙

### 사건번호

- `D...`: 디자인 사건(2026-09-16 사용자 확정). `D261119-JP`처럼 국가코드를 보존하고 추가 접미사를 삭제하지 않는다. 분류만으로 별칭·패밀리·그룹 관계를 만들지 않는다.

- `PP...`: 상상플러스가 관리하는 국내 특허
- `PPT...`: 상상플러스가 관리하는 가출원 사건
- 그 밖의 사건: 상상특허 관리
- 국내 `P...`: 국가코드 접미사가 없음
- `Pxxxxxx-PRO#`: 기획특허 `Pxxxxxx`의 우선권 기초 출원이며 그 자체를 별도 사건으로 관리
- `-US`, `-JP`, `-CN`, `-EP` 등: 해당 국가 사건이며 뒤에 추가 접미사가 올 수 있음
- `-PCT`: PCT 출원
- `-RE`: 동일 사건의 재출원
- `S...`: 과제·인증·기타 컨설팅을 포함한 기타 사건
- `AT251009` 형식: 심판 사건
- `T...`: 상표 사건 (2026-09-11 사용자 확인)
- `P...-S1`, `P...-S2`: 시리즈 내 각각 1번·2번 사건. 각각 전체 번호로 별도 식별하며 그룹 생성은 별도 확인.
- `P...-DIV1`, `P...-DIV2`: 원 사건의 1번째·2번째 분할출원. 원 사건과 연결하되 각각 전체 번호로 식별하는 별도 사건.
- `P...-CN(PA)`, `P...-S1-CN(PA)`: 중국 가출원 사건. `(PA)`까지 식별자에 포함하며 서비스·업무 상태를 자동 확정하지 않음.
- 2026-09-14 추가 확인: `-CN`은 정규 중국 출원, `-CN(PA)`는 중국 가출원이다. 전체 번호가 다르므로 별칭으로 자동 병합하지 않는다. 중국 가출원은 보통 우선심사용이지만 개별 사건의 목적을 일괄 확정하지 않는다. 사건등록 요청과 완료 회신의 번호가 충돌하면 완료 회신에 명시된 EasyPAT 번호를 우선한다. 그 외 충돌은 검토 대상으로 남긴다.

한 메일에서 관련된 여러 사건의 전체 관리번호를 명시하면 모두 연결한다. 원출원·시리즈·해외출원이 함께 표시된 경우에도 하나의 기본번호로 축약하지 않으며, 메일 연결과 그룹 소속은 별도로 판단한다.

정규식만으로 확정할 수 없는 새 형식은 원문 문자열을 보존하고 `unknown_pattern` 검토 항목으로 올린다.

2026-09-14 사용자 확인: 그룹 종류에는 포트폴리오, 시리즈, 정부지원사업 등이 있다. 종류는 별도 필드로 저장하고 기타 종류도 직접 입력할 수 있다. 기존 미지정 그룹은 `미분류`로 유지한다. 그룹 구성원·대표 사건은 종류와 별도로 확인한다. 한 사건의 여러 그룹 소속을 허용하며 같은 대표 사건의 다른 그룹은 별도 G 식별번호를 입력한다(예: GP261960, GP261960-2). 식별번호를 자동 생성하거나 시리즈·동일 고객을 근거로 그룹을 확정하지 않는다.

운영 반영 시에는 EasyPAT MCP의 전체 번호 정확 일치 결과를 우선하고, 조회할 수 없으면 사건등록 완료 메일, 업무관리 Excel의 현재 사건번호 열 순으로 대조한다. 사건등록 요청 메일은 완료 근거가 아니다. Excel에서 종류·대표 후보·전체 구성원이 직접 확인된 배치만 고정 파일 해시와 셀 범위를 남겨 반영한다. 새 사건 껍데기는 `excel` 추정값으로 저장하며 사용자가 확정한 사건으로 표시하지 않는다. 그룹 화면과 Wiki에는 그룹 종류뿐 아니라 대표 사건과 전체 구성원을 함께 표시한다.

번호 형식이 정의되지 않았거나 전체 구성원이 확인되지 않은 묶음은 `group_candidate_review` 규칙 실행으로 별도 기록한다. 이 실행은 원본 파일 해시, 확인된 번호, 원문 번호, 예상·확인 건수, 보류 이유, 사용자 질문과 셀 범위를 `input_snapshot`, `decision_run`, `decision_item`, `decision_evidence`에 남긴다. 검토 항목은 `/analysis`의 `그룹 확인 대기`에 표시하며 사건이나 그룹을 자동 생성하지 않는다.

회사·자연인 관계 후보는 `matter_linker`가 필드별 근거와 함께 반환하고 `risk_verifier`의 독립 검증 후 사용자 수락으로 반영한다. 회사 여부와 회사의 개인사업자·법인·미정 구분은 별도 필드로 유지한다. 회사명 유사성·동명이인만으로 병합하지 않는다. 자연인의 소속 회사나 법적 출원인 지위는 연락처라는 사실과 구분한다. 기존 메일 연결의 전체 번호 일치 감사는 규칙 실행으로 기록하며 불일치 표시는 오연결 확정이나 삭제를 뜻하지 않는다. 감사·관계 검토 대기 항목에는 대시보드에서 사용자 답변을 남길 수 있고, 원 판단과 답변은 별도 이력으로 보존한다.

### 업무·서비스·상태

- 업무종류 예: 출원, 중간사건, 등록
- 서비스종류 예: 일반출원, 우선심사출원, 메이킹, 기획, 가출원
- 업무단계 예: 출원, 중간사건, 등록
- 현재상태는 단계 안에서 세분화한다.

출원 단계의 기본 흐름은 `사건 등록 → 초안작성착수 → 초안 송부 → 고객 회신 → 수정안 송부 → 출원 지시 → 출원 → 우선심사 신청 → 우선심사 보완`이다. 사건 등록 당일을 기산일, 첫 입금일을 착수일로 기록한다. 초안작성착수는 비용 조건 충족 여부와 연결하며 선입금 충족 시 내부기일을 기본 1개월로 계산하되 확정 전 검증한다.

중간사건 유형은 `1OA`, `2OA`, `재심사청구`, `거절결정` 등을 별도 값으로 둔다. 상태 흐름은 `의견통지 → 보정안송부 → 고객 회신 → 수정안 송부 → 제출지시접수 → 제출완료`이고, 고객을 거치지 않는 경우 `의견통지 → 제출완료` 전이를 허용한다.

등록 단계에는 `등록결정(통지)`, `등록완료`를 두고, 등록결정 시 분할출원 여부·분할출원 착수·분할출원 완료를 연관 업무로 관리한다.

비용 처리 방식은 `선입금(완납)`, `착수금(2회)`, `단계별(3회 이상)`, `후청구`로, 자금 출처는 고객·정부지원금 등을 별도 필드로 기록한다.

## 7. Action 판정과 담당자 정책

담당자1은 실제 수행자, 담당자2는 담당자1을 관리하는 팀장이다. DB는 직접 영업한 사람, 수임자는 기존 고객으로부터 영업한 사람이다.

Action은 다음 혼합 기준으로 만든다.

1. 장진태 님에게 직접 요청된 업무는 장진태 Action 후보로 만든다.
2. 박준호 변리사 또는 황현우 과장에게 위임된 업무는 해당 팀원을 수행자로, 장진태 님을 관리 책임자로 둔다.
3. CC 메일은 기본적으로 참고다. 다만 승인, 재배분, 기한 통제, 팀원 진행 확인 또는 직접 회신의 근거가 있으면 장진태 Action 후보로 만든다.
4. 보낸 메일에서 장진태 님이나 팀원이 후속 조치를 약속한 경우도 Action 후보로 만든다.
5. 완료를 뒷받침하는 메일이 확인되어야 자동 완료 후보를 만든다. 애매하면 기존 Action을 닫지 않는다.

팀원용 Action도 장진태 님의 관리 화면에만 표시하고, 상태 변경은 장진태 님이 대신 수행한다.

## 8. LLM 모델 라우팅

프로젝트의 라우팅 원본은 `config/llm-routing.toml`과 `config/agents/*.toml`이다. 주 Codex 작업이 이 설정을 읽고 하위 작업을 시작할 때 모델과 추론 강도를 명시한다. 모델명을 애플리케이션 코드에 흩어놓지 않는다.

| 동작 | 담당 에이전트 | 기본 모델·추론 | 출력 |
|---|---|---|---|
| 메일 사실 구조화 | `mail_intake` | `gpt-5.6-terra` / high | 사실·근거 후보 (2026-09-16 사용자 승인 변경) |
| 사건·업무 연결 | `matter_linker` | `gpt-5.6-terra` / high | 연결 후보·신뢰도 |
| Action 판단 | `action_analyst` | `gpt-5.6-sol` / high | Action 후보 |
| 고위험 교차검증 | `risk_verifier` | `gpt-5.6-sol` / high | 확인·반려·사람 검토 |
| Wiki 개정안 | `wiki_synthesizer` | `gpt-5.6-terra` / medium | 새 Wiki 버전 후보 |

모델 변경은 장진태 님이 이 프로젝트에서 요청하면 `config/llm-routing.toml`과 해당 에이전트 TOML의 `model`, `model_reasoning_effort`를 함께 수정하는 방식으로 수행한다. 변경 시 설정 변경 이벤트와 이후 `decision_run`에 실제 사용값을 남긴다. 사용할 수 없는 모델이면 임의 대체하지 않고 사용자에게 알린다.

LLM을 호출하지 않는 동작은 메일 중복 제거, 폴더 제외, 사건번호 정규식 검사, 날짜 파싱, EasyPAT MCP의 허용 필드 조회·검증·기록, 명백한 상태 전이 검증, DB 트랜잭션, 대시보드 조회·저장이다.

## 9. 처리 파이프라인

1. 사용자가 기간을 지정해 Codex에 갱신을 요청하면 `work_refresh_run`에 요청 접수 시각과 검토 대상 기간을 먼저 고정한다. 요청 접수 시각은 원본 메일 시각이나 처리 완료 시각으로 다시 계산하지 않는다.
2. Outlook 읽기 어댑터가 허용 폴더와 보낸 편지함을 읽고 Message-ID와 본문 해시로 중복을 제거한다. 이 수집 시도는 `sync_run`으로 남기고 상위 `work_refresh_run`에 연결한다.
3. 코드가 본문 정규화, 명백한 관리번호·주소·날짜 추출과 Thread 연결을 수행한다.
4. 주 Codex 작업이 `easypat_status`를 확인하고, 추출된 전체 당소관리번호를 `easypat_get_matter_summary`로 정확 조회한다. 상태·진행 근거가 필요할 때만 나머지 허용 도구를 순서대로 사용한다.
5. EasyPAT 결과는 허용 필드만 신뢰된 CLI 브리지로 기록한다. 결과 번호 불일치, 0건·복수 결과, 연결 실패는 차순위 값을 EasyPAT으로 가장하지 않고 검토 대상으로 남긴다.
6. 필요한 메일만 `mail_intake`가 사실 후보로 구조화한다.
7. 결정적 규칙으로 연결되지 않는 항목을 `matter_linker`가 사건·업무 후보에 연결한다.
8. `action_analyst`가 장진태·팀원 Action 후보를 만든다.
9. 기일, 제출, 등록, 비용 또는 사건 충돌 등 고위험 항목만 `risk_verifier`가 EasyPAT 관측과 원문을 독립 검증한다.
10. 주 Codex 작업이 스키마·상태 전이·중복을 검증하고, 확정 가능한 이벤트를 SQLite에 원자적으로 반영한다.
11. `wiki_synthesizer`가 확정 이벤트로 Wiki 새 버전 후보를 만들고 주 작업이 저장한다.
12. 대시보드는 사건·업무·Action·Wiki와 마지막 EasyPAT 확인 투영을 새로 읽는다. 사용자의 수정은 다시 이벤트로 기록된다.
13. 비교기가 모델의 필드별 판단과 사용자 최종값을 비교하여 피드백 및 회귀 사례 후보를 만든다.
14. 반복 오류의 개선안은 전체 회귀 평가와 장진태 님의 승인을 통과한 뒤에만 규칙·프롬프트·라우팅에 반영한다.

각 대상 메일은 `work_refresh_mail`, 단계 체크포인트는 `work_refresh_stage`, 적용·보류 결과와 원본 근거는 `work_refresh_result`에 기록한다. `source_at`은 근거 자체의 시각이고 `requested_at`은 사용자가 업무 정리를 요청한 시각이며 `completed_at`은 처리가 끝난 시각이다. 세 시각은 서로 대체하지 않는다.

한 단계가 실패해도 이미 확정된 원본 메일과 이벤트는 유지한다. 재실행은 같은 `work_refresh_run`의 마지막 정상 `work_refresh_stage` 이후부터 이어가며, 개별 메일 수집 재시도는 연결된 `sync_run`으로 구분한다. 같은 Message-ID·결과 키·이벤트 키를 중복 반영하지 않는다.

업무 정리 실행 관리자는 `dashboard/lib/work-refresh.ts`가 담당한다. 실행 상태는 `requested → collecting → analyzing → review_pending → applying → completed`를 기본 흐름으로 사용하며, 오류가 있으면 `failed` 또는 `partial`로 남긴다. 실패·부분 완료 실행의 새 단계는 시도 번호를 증가시켜 재개하고 이전 시도는 삭제하지 않는다. 분석 결과가 들어오면 `decision_run`의 정확한 단계 ID와 메일별 coverage를 근거 결과로 연결하며, 같은 단계 결과의 재수신은 중복 반영하지 않는다.

로컬 API는 실행 목록·상세·생성, 단계 시작·완료·실패, 결과 기록, 최종 완료 판정을 `/api/work-refresh` 계열로 제공한다. 기존 `/api/mail-sync`는 요청 접수 시 실행과 수집 단계를 먼저 만들고, 수집한 신규·기존 메일을 모두 대상 목록에 연결한 뒤 수집 단계를 종료한다. 수집 성공만으로 전체 업무 정리를 완료 처리하지 않고 다음 분석 또는 검토를 기다리는 `review_pending` 상태로 둔다.

008 적용 이전의 `sync_run`은 당시 전체 분석·반영 범위를 재현할 근거가 없으므로 `work_refresh_run`으로 소급 생성하지 않는다. 새 추적 이력은 008 적용 이후 사용자가 요청한 실행부터 쌓는다.

## 10. 대시보드 정보 구조

기본 화면은 `PROJECT SELECTOR` 하나만 유지하고 `ACTIVE PROJECTS`처럼 중복되는 선택 UI는 두지 않는다.

- 사건 선택: 당소관리번호, 그룹, 회사, 자연인으로 검색
- 사건 개요: 관리 사무소, 국가, 업무종류, 서비스종류, 담당자, 비용 조건
- EasyPAT 원본 확인: 마지막 확인 시각, 허용 필드별 관측값, 현재 운영값과의 충돌
- 현재 업무: 단계, 현재상태, 내부기일·법정기일, 근거와 신뢰도
- Action: 장진태 본인과 팀원별 구분, 상태·기한·중요도 편집
- 메모: 사용자 메모와 LLM 요약을 명확히 구분
- Wiki: 최신 요약, 버전 이력, 근거 메일·이벤트
- 검토함: 미확정 사건 연결, 출처 충돌, 고위험 판단, 새 사건번호 패턴, 불완전 그룹 구성원
- 동기화: 최근 1일·1주일·기간 지정, 마지막 실행 결과
- 업무 정리 실행 현황: 검토 대상 메일 기간, 실제 검토된 메일 범위, 요청 접수 시각(`requested_at`), 처리 완료 시각, 단계별 진행률과 적용·보류·오류 건수
- 문서 자동수집: 다음 예약, 마지막 실행, 복구 시작점, 통지별 단계·첨부 수, 예상·완료 ZIP, 확인 필요·실패와 재개 지점
- 모델 설정: 동작별 에이전트·모델·추론 강도와 변경 이력
- 판단 비교: 모델 제안값, 사용자 최종값, 수정 이유, 근거, 당시 버전
- 개선 검토: 반복 오류, 개선안, 회귀 평가 전후 결과, 적용·보류·반려

업무 정리 실행 현황은 최신 실행을 기본으로 보여 주고, 이전 실행은 접힌 이력에서 선택한다. 사용자가 새 이메일 갱신을 요청하면 API 응답의 `workRefreshRunId`로 해당 실행을 즉시 다시 조회한다. 메일의 최신 시각을 최종 반영 시각으로 오인하지 않도록 화면에서는 `requested_at`을 **최종 반영 기준 시각 · 요청 접수**로 표시하며, 근거 메일 시각과 처리 완료 시각을 별도 항목으로 유지한다.

문서 자동수집은 `/downloads`에서 조회한다. 실행 중에는 원장만 짧은 간격으로 읽고 화면 조회로 Outlook·EasyPAT·파일 작업을 시작하지 않는다. 모호한 근거는 `/analysis`, 사건 정보는 `/matters`로 연결한다. 게시 완료 뒤 중간사건 대응 프로젝트의 생성·Codex 연결·접수·분석·전략·초안·검수·승인·제출은 별도 `/responses` 화면에서 13단계로 표시한다. 다운로드 상태와 대응 프로젝트 상태는 합치지 않는다. 화면과 `/api/downloads` 계약은 `docs/NOTICE_DOWNLOAD_DASHBOARD_PLAN.md`, 프로젝트 구조와 사용자 행위는 `docs/NOTICE_RESPONSE_PROJECT_WORKFLOW.md`, 진행 화면은 `docs/NOTICE_RESPONSE_PROGRESS_DASHBOARD_PLAN.md`를 기준으로 한다.

대시보드 API는 localhost 요청만 허용하고, 상태 전이 검증·낙관적 잠금·트랜잭션·감사 이벤트를 적용한다. LLM이 만든 문자열을 SQL이나 셸 명령으로 실행하지 않는다.

## 11. 구현 순서와 완료 기준

### 1단계: 데이터 기반

- [완료] SQLite 스키마, 마이그레이션, 무결성 검사, 백업·복구
- [완료] 사건번호 파서와 출처·신뢰도 모델
- [완료] 사건 선택 및 상태·메모·Action CRUD

구현 원본은 `dashboard/db/migrations`, `dashboard/lib/work-db.ts`, `dashboard/lib/matter-number.ts`, `dashboard/app/matters/page.tsx`, `dashboard/local-api.ts`이다. 자동 테스트는 분리된 임시 DB에서 CRUD·감사 이벤트·백업 복원을 검증한다. 2단계 메일 수집은 1단계와 분리하여 다음 시작 지시 전에는 실행하지 않는다.

### 2단계: 메일 수집

- [완료] Outlook 읽기 전용 어댑터와 제외 폴더 검증
- [완료] 1일·1주일·기간 지정 수집
- [완료] EntryID·Message-ID·본문 해시 저장, 중복 방지와 Conversation ID 보존
- [완료] 명시적 관리번호 연결과 날짜별 규칙 기반 중요내용 1차 요약

Outlook 수집 원본은 `dashboard/scripts/Export-OutlookMail.ps1`이며 대상 저장소는 기존 VBA와 같은 `jtjang@sspat.net`이다. 수집 파일은 운영 DB 옆 `mail-staging`에 일시 생성되고 DB 반영 여부와 관계없이 삭제된다. 2단계 요약은 새 메시지 본문 앞부분을 근거로 하는 `deterministic` 유형이며, LLM이 판단한 요약으로 가장하지 않는다. 3단계에서 `mail_intake`의 구조화·중요도 판단과 실행 이력을 추가한다.

### 3단계: Codex 분석

- [완료] 프로젝트 에이전트별 구조화 출력 계약과 CLI 실행 연결
- [완료] 사건 연결·Action 후보·독립 고위험 검증 및 검토 화면
- [완료] LLM 실행 기록, 입력 스냅샷·정확한 원문 인용 검증, 프롬프트 버전 관리
- [완료] 후보 수락·수정·반려와 필드별 사용자 피드백·확정 이벤트의 원자적 기록

미등록 사건 반영은 기존 사건 연결과 구분한다. `matter_linker`는 사건등록 완료 원문이면 `registration_mail`, 현재 비인용 메시지가 전체 당소관리번호와 같은 사건의 실질 업무를 직접 보여주면 `active_matter_mail` 후보를 기록하고 `risk_verifier`가 독립 검증한다. 주 작업의 `applyVerifiedRegistration`은 백업 사본 검사 후 사건 식별 레코드와 해당 근거 메일 연결만 만든다. 완료 메일은 `registration_mail`, 현재 업무메일 추정은 `mail_inference`로 저장하며 모두 `user_confirmed=0`을 유지한다. 사용자 피드백이나 학습 성공 사례는 자동 생성하지 않는다. 업무 상태·기일·담당자·회사 관계·그룹·별칭은 이 절차의 변경 대상이 아니다. 사건등록 요청, 권리 등록결정만 있는 메일, 입금만 있는 메일, 과거 인용, 외부 참조번호만으로 만들지 않으며 기존·보관 사건 충돌과 변경된 원문·추가 메일·검증 반려는 차단한다. 같은 후보의 재실행은 중복 생성하지 않는다.

Wiki의 구체적 계층·대상별 페이지·날짜별 기록 및 4단계 경계는 `docs/LLM_WIKI_DESIGN.md`를 따른다. 구현은 `dashboard/lib/analysis.ts`, `dashboard/scripts/analysis-cli.ts`, `config/analysis-contract.md`, `/analysis`이다. 모델 실행은 현재 Codex의 전문 작업을 사용하고 별도 LLM API를 호출하지 않는다. 분석 표본 검증과 전체 운영 메일 처리 완료를 구분한다. 3단계에서는 후보 검토 및 메일 단위 확정 요약까지만 저장하며, 회사·사람·그룹별 요약 투영과 Wiki 게시·버전 탐색은 4단계다.

### 4단계: Wiki와 운영 안정화

- [완료] 사건·회사·자연인·그룹 Wiki 화면, 날짜별 기록, 버전 비교와 문장별 근거 탐색
- [완료] CLI 재처리·실패 이력, 입력/버전 충돌 게시 차단, 검토 대기 개정안
- [완료] 1~4단계 회귀 테스트와 Wiki 포함 백업 복원 테스트

구현 범위와 실제 운영 검증은 `docs/PHASE4_VERIFICATION.md`를 따른다. `wiki_entry`는 사용자 기록과 독립 검증된 메일 기재 관찰을 구분하며, 기존 비고·업무 상태를 변경하지 않는다. `entity_wiki_revision`은 기존 사건 전용 `wiki_revision`을 삭제하지 않고 대상 4종으로 확장한다. `wiki_draft`의 게시 시 당시 입력 및 현재 Wiki 버전을 재확인한다. 전문 에이전트의 문장별 근거 계약은 `config/wiki-contract.md`이고 실행 라우팅은 기존 Terra/medium이다.

### 5단계: 통지서 자동 다운로드 진행 화면

- [계획] 일일 감지 실행과 단계 이벤트 원장
- [완료] `/downloads` 예약 상태·작업 목록·실행 이력·상세 화면
- [완료] `/api/downloads` 읽기 API와 민감정보 제거
- [완료] 허용 상태의 다시 검증·재개 요청 및 중복 차단
- [완료] 게시 완료 통지의 대응 프로젝트 안전 생성과 사용자 행위 표시
- [완료] `/responses` 프로젝트 초기화부터 제출 결과까지 13단계 진행 화면
- [완료] 단계별 산출물 해시, 사용자 승인, Codex 작업 링크와 승인 무효화 이력

구현 순서와 검수 기준은 `docs/NOTICE_DOWNLOAD_DASHBOARD_PLAN.md`와 `docs/NOTICE_RESPONSE_PROJECT_WORKFLOW.md`를 따른다. 의견제출통지서의 기존 P261252 완료 원장을 먼저 읽기 전용 화면과 임시 프로젝트 dry-run에서 검증하고, 거절결정과 우선심사 보완의 실제 표본·전용 지침 검증 후 종류별 기능 플래그를 활성화한다.

화면 구현 완료는 메일 98건 전체 분석 완료를 뜻하지 않는다. 회사·자연인·그룹 자동 식별/병합 및 각 대상별 자동 메일 지식 연결은 아직 별도 운영 검토가 필요하며, 근거 없는 대상 정보나 요약을 채우지 않는다.

각 단계는 실제 메일을 이동하거나 삭제하지 않는 dry-run으로 먼저 검증한다. 운영 전에는 제외 폴더 본문 읽기 0건, 보낸 편지함 포함, 재수집 시 신규 중복 반영 0건, 사용자 확정값 보존, 대시보드 변경 이벤트 생성, 재실행 멱등성을 확인한다.
