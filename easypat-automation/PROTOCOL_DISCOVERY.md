# EasyPAT HTTPS 통신 규격 조사

## 사건 검색 관찰 결과

2026-09-14에 로그인된 EasyPAT 3.44에서 `OurRef` 정확 일치 검색을 한 번 실행하고 새로 발생한 트래픽만 분리해 확인했다.

- 대상: `https://mssql2.easypnp.co.kr:8443/servlet/Jbori`
- 전송: HTTPS POST, HTTP/1.1
- 관찰된 TLS: TLS 1.2
- 응답: 두 업무 요청 모두 HTTP 200
- 요청 본문: form-data
- 공통 필드명: `connection`, `count`, `command`, `sql`
- 순서 1: 검색 결과 개수 조회, 38바이트 응답, `recCount=1`
- 순서 2: 검색 결과 행 조회, 358바이트 응답
- 화면 대조: 정확히 1건이며 당소관리번호, 국내/특허 구분과 사건종결 상태가 일치

원본 SQL, 세션 쿠키, 인증 헤더와 전체 응답 원문은 프로젝트에 복사하지 않았다. 운영 어댑터는 임의 SQL 입력을 받지 않고 `search-matter` 고정 함수가 두 읽기 요청을 생성하도록 설계한다.

## 관찰 중 안전조치

- `Ignore server certificate errors`는 활성화하지 않았다.
- 필요한 검색 한 번만 수행했다.
- 저장·수정·삭제 요청은 발생시키지 않았다.
- 확인 후 시스템 프록시와 HTTPS 캡처를 모두 비활성화했다.

## 남은 2단계 관찰 항목

### 임시 Fiddler MCP 연결

2026-09-14에 Fiddler Everywhere의 로컬 MCP 서버를 Codex CLI용으로 구성했다. Fiddler의 MCP 출력 정제 기능이 활성화된 상태였고, 로컬 감지 API에서 설정 파일이 존재하며 유효하다는 응답을 확인했다. API 키 값은 프로젝트, 로그 또는 대화에 복사하지 않았다.

이 연결은 캡처된 요청을 분류하고 검증된 읽기 템플릿의 지문을 등록하는 개발 단계에서만 사용한다. 운영 EasyPAT MCP 서버가 직접 HTTPS 요청을 수행할 수 있게 되면 Fiddler MCP 키를 폐기하고 Codex의 임시 연결 설정을 제거한다. 현재 실행 중인 Codex 작업은 새 MCP 도구를 동적으로 불러오지 못하므로 재시작 후 세션 판독을 계속한다.

### 사건 상세 화면 진입

2026-09-14에 P261793 검색 결과를 선택해 상세 화면을 열었다. 이 동작에서 새 HTTPS POST 8건이 관찰됐다. 참조 코드 조회, 사건 본문 조회와 관련 개수 조회 등 읽기 요청 외에 EasyPAT이 자동으로 상태 관련 `UPDATE` 요청 1건을 전송했고 서버는 HTTP 200과 한 행 처리 표시를 반환했다.

따라서 UI에서 상세 화면을 여는 동작은 읽기 전용으로 분류할 수 없다. 원본 문장과 인증정보는 저장하지 않았으며, 발견 즉시 추가 분석을 중단하고 프록시와 HTTPS 캡처를 껐다. 직접 통신 어댑터에서는 상세 화면 진입 흐름 전체를 재생하지 않고, 검증된 읽기 요청만 분리하기 전까지 `get-matter-detail`을 차단한다.

`src/protocol/read-only-guard.mjs`에 통신 어댑터의 1차 격리 계층을 구현했다. `SELECT`와 읽기 전용 CTE만 허용하고, 여러 문장을 묶는 요청도 모든 문장이 읽기 전용일 때만 통과한다. `UPDATE`, `INSERT`, `DELETE`, `MERGE`, 프로시저 실행 및 스키마 변경 토큰이 하나라도 있으면 전체 배치를 거부하며 일부 요청만 선행 실행하지 않는다. 로그용 요약에는 원문을 포함하지 않는다.

`src/protocol/template-fingerprint.mjs`는 격리된 읽기 요청을 내부 템플릿 ID와 SHA-256 지문으로 검증한다. 명령 종류, 문장 수와 지문이 모두 일치해야 통과하며 한 글자라도 달라지면 거부한다. 운영 레지스트리에는 원문을 저장하지 않는다. 현재 상세조회 후보 3개는 ID만 부여했고 지문이 아직 확정되지 않았으므로 모두 비활성 상태다.

`src/register-template.mjs`는 검증된 캡처 어댑터가 표준입력으로 전달한 메모리 내 JSON만 받는다. 인증 관련 필드와 쓰기 문장을 먼저 거부하고, 템플릿의 명령 종류와 문장 수가 일치할 때 SHA-256 지문만 레지스트리에 기록한다. 원문을 명령행 인자로 받거나 출력하지 않으며, 활성화된 지문은 다른 값으로 교체할 수 없다.

### 남은 관찰 항목

#### MCP 판독 후 확인 및 정정

사용자가 민감한 캡처의 MCP 판독을 승인한 뒤, 대상 호스트·경로·POST로 필터링된 검색 2건과 상세 진입 8건을 확인했다. 상세 진입 8건의 실제 요청 본문 `command` 필드를 해석한 결과 읽기 명령 6건과 `UPDATE` 2건(세션 172, 178)이 확인됐다. 앞선 UI 확인에서 기록한 수정 1건은 부분 관찰이었다. 추가 수정의 대상·영향 행 수는 아직 확정하지 않았다. 이번 작업에서는 기존 세션만 읽었으며 서버 요청을 재전송하지 않았다.

세션 166의 참조 코드 SELECT 3개는 원문 정제 표시가 없어 후보 SHA-256 지문을 계산했다. 나머지 7건은 SQL에 `!!!sanitized!!!`가 포함되어 정확한 지문 계산을 거부했다. 해당 명령이 SELECT라는 사실만으로 본문 전체를 읽기 전용이라고 확정하지 않는다. 후보 지문과 세션별 결과는 `config/protocol-observations/detail-mcp-classification.json`에 기록했으며 운영 템플릿 레지스트리는 계속 비활성 상태다.

`src/protocol/fiddler-capture.mjs`는 MCP 오류/안내문과 실제 세션 JSON을 구분하고, 인가 엔드포인트·form encoding·중복 키·문장 수·인덱스·정제 표시를 검증한다. `src/inspect-capture.mjs`는 표준입력으로 세션 JSON을 받아 원문과 쿠키 없이 분류·지문만 출력한다. 원본 캡처를 파일이나 명령행 인자로 저장하지 않는다. SELECT INTO와 외부 데이터 접근 토큰도 읽기 후보에서 제외한다. 이 토큰 검사는 보수적 사전 필터이며 SQL 파서나 의미 검증을 대신하지 않는다.

다음 연결 과제는 정제 전 원문을 신뢰된 로컬 프로세스 안에서 검증·해시하고 결과만 전달하는 경로다. MCP 출력 정제를 끄거나 가려진 값을 추측해서 지문을 등록하지 않는다. 지문만으로 실행 요청을 재구성할 수 없으므로, 이후 고정 요청 보관·매개변수 바인딩 방식도 별도 구현·검증해야 한다. 자동 로그인·문서 다운로드·정보 추출·운영 MCP는 아직 완성되지 않았다.

1. 상세 진입 묶음에서 읽기 요청만 오프라인으로 분류하는 방법
2. 진행사항 목록 조회 요청
3. 문서 목록 조회 요청
4. 파일 다운로드 요청과 응답 헤더
5. 로그인 및 세션 갱신 요청 — 자격 증명 값은 저장하지 않고 필드 구조와 성공·실패 상태만 기록

## 2026-09-15 로컬 원문 지문 검증

Fiddler 공식 문서에서 [SAZ/HAR 내보내기](https://www.telerik.com/fiddler/fiddler-everywhere/documentation/collaboration/exporting-and-importing)와 [SAZ 로컬 저장 위치](https://www.telerik.com/fiddler/fiddler-everywhere/documentation/knowledge-base/fiddler-archives)를 확인했다. 기본 `.fiddler` 위치에는 기존 SAZ/HAR 파일을 찾지 못했다. 새 원문 파일을 만들지 않고 Fiddler의 Form-Data `sql` 필드에 있는 `Copy Value` 기능으로 세션 168과 170의 SQL만 로컬 클립보드에 복사했다. 인증 헤더·쿠키 필드는 복사하지 않았다.

`scripts/Inspect-FiddlerClipboard.ps1`은 복사된 값을 UTF-8 표준입력으로 `src/inspect-copied-statement.mjs`에 전달한다. SQL을 명령행 인자로 사용하거나 출력하지 않으며 네트워크 요청도 보내지 않는다. 원문은 프로세스 메모리에서 검사하며 SHA-256 후보 지문만 반환한다. `-ClearCopiedValue`는 현재 클립보드가 방금 검사한 값과 같을 때만 완료 안내문으로 교체한다. Windows 클립보드 기록·동기화의 보존 여부는 이 도구가 보장하지 않는다.

실제 168·170의 원문 지문을 계산했고 이전 166의 결과와 함께 `config/protocol-observations/local-read-fingerprints.json`에 기록했다. 두 SQL은 읽기 토큰 필터를 통과했지만 `'P261793'` 문자열은 발견되지 않았다. 내부키를 사용하는지, 검색 결과의 어떤 필드와 연결되는지는 아직 확인하지 않았다. 세션 이름/역할은 UI에서 관찰한 선택에 근거하며, 단일 SQL 값 자체는 요청 URL이나 세션 ID를 증명하지 않는다.

따라서 후보 3개의 정확한 캡처 지문 확보는 완료했으며, 활성 템플릿 등록·다른 사건에 대한 매개변수 처리·실시간 실행은 미완료다. 이후 검색 응답의 내부 식별자 연결과 보호된 고정 요청 보관 방식을 검증한 뒤 활성화한다. 이번 단계의 UI/클립보드 사용은 개발 중 규격 검증용이며 운영 자동화에는 포함하지 않는다.

## 검색 결과와 상세 키 연결 검증 준비

`src/protocol/matter-linkage.mjs`와 `src/inspect-linkage.mjs`를 구현했다. 로컬 표준입력 JSON의 `matterReference`, `searchRows`, `detailSql`을 받아, 정확한 OurRef 단일 행과 기존 상세 후보 지문을 확인한다. SQL에서 보수적으로 추출한 등식의 리터럴과 검색 행의 값을 비교해 일치한 필드명만 반환한다. 원문, 쿠키, 내부 식별자 값은 출력하지 않는다. 동일 값이 여러 필드에 있으면 모호한 것으로 표시하고, 주석·문자열 안의 SQL처럼 보이는 텍스트는 조건으로 해석하지 않는다.

사용 방법은 `node src/inspect-linkage.mjs 168` 또는 `170`에 신뢰된 로컬 파서가 만든 JSON을 표준입력으로 전달하는 방식이다. 이 CLI는 Fiddler resultset 본문을 행으로 변환하는 파서나 실제 데이터 연결을 아직 포함하지 않는다. 테스트용 인공 입력만으로 CLI를 활성 조회 함수라고 간주하지 않는다. 단일 값의 일치는 연결 후보 증거이며 기본키 의미나 다른 사건의 안전한 매개변수 바인딩을 증명하지 않는다.

2026-09-15 세션 119의 전체 상세 읽기와 출력 축소 재시도가 자동 승인 검토에서 거부됐다. 이전 캡처 판독 승인이 있었으나 검토기는 해당 세션 본문·쿠키·내부 식별자가 작업에 전달되는 구체적 승인이 필요하다고 판정했다. 원문을 다른 경로로 가져오는 재시도는 중단했다. 실제 검색 응답 대조는 미완료이며 `config/protocol-observations/matter-linkage-status.json`에 상태를 기록했다. 독립적인 로컬 검증기 구현과 합성 데이터 테스트는 완료했다.

### 추가 승인 후 실제 P261793 대조 완료

사용자가 세션 119의 구체적 판독을 추가 승인한 뒤 MCP 응답을 받았다. `idx`, `ourref` 등 필요한 값은 MCP 정제로 가려져 있었으며, Fiddler 응답 Body의 복사 기능으로 기존 원본을 로컬 검사기에 전달했다. 요청을 재전송하거나 Fiddler 정제 설정을 변경하지 않았다.

관찰된 응답은 `text/resultset`이며 SOH(U+0001)로 필드를, CRLF로 레코드를 구분한다. 처음 네 레코드는 필드명·타입·길이·플래그이고 이후는 데이터 행이다. 문자 값은 큰따옴표로 묶여 있으며 숫자 키는 문자열로 보존해 정밀도를 잃지 않는다. `src/protocol/resultset.mjs`는 이 형식만 파싱하며 정제 표시·열 개수 불일치·잘못된 인용을 거부한다.

`src/inspect-search-result.mjs`로 검색 결과가 정확히 `ourref=P261793`인 한 행임을 확인했다. 원본 `idx`는 출력하지 않고 메모리 비교용 SHA-256만 반환했다. `src/inspect-detail-keys.mjs`는 복사된 상세 SQL이 기존 168·170의 지문과 일치하는지 먼저 확인한 뒤, 등식 리터럴의 해시를 계산했다. 원문과 내부 값의 해시는 프로젝트에 기록하지 않았다.

실제 값 비교 결과 검색 `idx`는 세션 168의 `idx` 한 조건, 세션 170의 `idx_parent` 11조건·`GRP_KEY` 한 조건·`idx_data` 한 조건과 일치했다. 필드명과 일치 횟수만 `config/protocol-observations/matter-linkage-evidence.json`에 기록했다. 검사한 현재 클립보드 값은 검사 완료 안내문으로 교체했다.

이로써 기존 P261793 캡처의 값 연결 대조는 완료됐다. 다만 한 사건의 값 일치가 각 테이블의 기본키 의미, 모든 업무의 키 연결 또는 일반적인 SQL 치환 안전성을 증명하지는 않는다. 운영 레지스트리와 실시간 상세조회는 계속 비활성 상태이며, 다음은 보호된 고정 요청 저장과 매개변수 위치 검증, HTTPS 클라이언트 및 자동 인증 구현이다.

## 고정 SELECT 클라이언트 및 HTTPS 전송 구현

2026-09-15 `src/protocol/fixed-read-client.mjs`와 `https-transport.mjs`를 추가했다. 클라이언트는 신뢰된 공급기에서 읽은 고정 SELECT 원문을 활성 레지스트리의 지문으로 확인하고, 등록된 전체 사건번호와 일치할 때만 요청 본문을 만든다. 공개 호출 입력으로 SQL·쿠키·임의 URL을 받지 않는다. `boundMatterReference`가 없는 기존 후보나 비활성 후보는 세션 공급기를 호출하기 전에 거부한다.

HTTPS 전송은 허용 URL과 POST, TLS 인증서 검증, 리다이렉트 거부, 전체 시간 제한, 스트리밍 크기 제한, Content-Type·UTF-8·응답 길이를 확인한다. 401/403은 세션 필요 오류이며 자동 재시도하지 않는다. 오류 메시지에는 원문 요청·쿠키·네트워크 라이브러리 원본 오류를 포함하지 않는다. 응답 헤더와 Set-Cookie도 업무 호출 결과로 반환하지 않는다.

검증은 합성 응답과 모의 네트워크로 수행했다. 실제 공급기, 자동 인증, 세션 갱신과 실제 서버 통신은 아직 검증되지 않았다. 관찰에서 확인한 idx 연결은 근거로 보존하며, SQL 전체에 대한 숫자 치환이나 추측한 쿼리를 작성하지 않았다. 현재 정책·레지스트리는 변경하지 않아 실시간 상세조회는 계속 차단된다. 상세 상태는 `config/protocol-observations/https-client-status.json`에 기록했다.

## 보호된 원문 저장소와 세션 공급기 연결

2026-09-15 Microsoft의 [DPAPI 문서](https://learn.microsoft.com/en-us/dotnet/standard/security/how-to-use-data-protection)와 [CredReadW 문서](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credreadw)를 확인하고 `src/security` 모듈 및 `scripts/WindowsSecretBroker.ps1`을 구현했다. DPAPI는 CurrentUser 범위와 앱 전용 추가 엔트로피를 사용한다. 저장 전·복호화 후 모두 지문을 검증하고 파일을 exclusive-create로 생성해 기존 파일을 덮어쓰지 않는다. 심볼릭 링크와 예상하지 못한 경로는 거부한다.

기본 Windows PowerShell의 스크립트 실행 제한으로 최초 합성 DPAPI 테스트가 실패했다. 이미 사용 중인 PowerShell 7 런타임으로 실행해 성공했으며 시스템 실행 정책은 변경하지 않았다. 브로커는 비밀정보를 인자로 받지 않고 비공개 표준입출력 파이프를 통해 로컬 부모 프로세스와만 교환한다. 원본 예외는 외부로 반환하지 않는다.

Fiddler에서 기존 세션 168·170의 SQL 값만 다시 복사해 지문 확인 후 `.local/templates`에 DPAPI 암호문으로 보관했다. 두 건 모두 복호화 후 원래 지문과의 일치를 확인했고 Git ignore 적용도 확인했다. 평문 파일은 만들지 않았다. 비교한 현재 클립보드 값은 완료 안내문으로 교체했다. 암호화 파일은 사용자가 삭제하거나 다른 Windows 환경으로 옮기면 재등록이 필요할 수 있다.

Windows 일반 자격 증명 `EasyPAT/Automation`을 읽는 구현은 포함했지만 실제 항목을 읽거나 생성하지 않았다. 사용자명/비밀번호를 읽는 시점은 검증된 로그인 어댑터가 연결된 이후다. 현재 `createSessionProvider`는 인증 규격 미검증 상태에서 즉시 멈춘다. 로그인 동시 호출 공유, 최대 1회 시도, 실패/추가인증 중단, 만료/무효화를 합성 테스트로 검증했다. 로그인 중 무효화되면 뒤늦은 응답이 세션을 되살리지 않도록 처리한다.

`src/runtime.mjs`로 암호화 저장소·세션 공급기·고정 HTTPS 클라이언트를 연결했다. 실제 원문 2건은 준비됐지만 자동 로그인 통신 구현·자격 증명 읽기 실검증·실제 서버 조회는 아직 미완료다. 정책과 활성 템플릿은 그대로 차단되어 있으며 이 단계에서는 서버 요청을 보내지 않았다.

## 로그인 규격 조사: 이전 캡처 그룹 추가 확인

사용자가 처음 제시한 실행 경로는 현재 파일시스템에서 찾지 못했다. 실행 중인 프로세스는 `C:\Program Files (x86)\EASYPAT S SSPAT\boriview.3.44.exe`이며 같은 설치 폴더에 `EASYPAT_S_SSPAT.exe`, `bori.3.44.dll`이 있다. DLL의 읽기 전용 문자열 검사에서 WinINet HTTP 함수, Cookie/Set-cookie와 dlgLogin 문자열을 확인했지만 이것만으로 인증 경로나 필드 구조를 확정할 수는 없다.

Fiddler의 최근 애플리케이션 그룹을 선택한 상태에서는 서버 요청 10건만 보였다. All Traffic으로 전환한 뒤 대상 호스트 필터를 다시 적용하자 기존 서버 요청 36건이 조회됐다. 그중 35건은 `/servlet/Jbori`, 세션 29 한 건은 `/EASYPAT_S_SSPAT/ip.jsp` POST이며 HTTP 200과 `text/html;charset=euc-kr` 응답 메타데이터가 보였다. 이 요청은 로그인 전후 통신의 후보일 뿐, 이름만으로 실제 인증 요청이라고 판단하지 않는다.

세션 29의 상세 읽기는 인증정보·쿠키·본문 노출 가능성을 이유로 자동 승인 검토에서 거부됐다. 해당 본문은 읽지 않았으며 다른 경로로 재시도하지 않았다. 구체적인 세션 판독 승인을 받은 뒤 요청 필드명·성공/실패 구조·쿠키 속성을 확인해야 한다. 후보 경로를 운영 정책에 추가하거나 해당 주소로 요청하지 않았다. 조사 상태는 `config/protocol-observations/authentication-discovery.json`에 기록했다.

독립적으로 `src/security/session-cookie.mjs`를 구현했다. [RFC 6265](https://www.rfc-editor.org/rfc/rfc6265)의 쿠키 도메인·경로·만료 개념을 참고하여 검증된 인증 어댑터 내부에서만 사용할 제한된 쿠키 선택기다. 지정된 이름의 쿠키 하나만 선택하고, 동일 HTTPS origin·요청 경로·만료·중복·헤더 삽입을 검증한다. 서버가 만료를 주지 않는 세션 쿠키는 명시된 로컬 재사용 한도를 적용하되 이를 서버 만료시간으로 표현하지 않는다. 범용 브라우저 쿠키 저장소나 EasyPAT 인증 규격 구현이 아니며, 실제 쿠키 이름·만료 방식은 여전히 확인이 필요하다.

### 추가 승인 후 인증 후보 판독

사용자가 세션 29 상세 판독을 승인한 뒤 기존 캡처를 MCP로 읽었다. 요청은 Content-Length 0이고 도구 결과에 요청 본문이 없으며 Cookie 헤더도 없다. 응답에는 Set-Cookie 헤더가 있지만 전체 값이 정제되어 이름·Path·만료를 확인할 수 없다. 응답 본문도 정제되어 있다. HTTP 200과 쿠키 발급만으로 사용자 인증 성공을 판단하지 않는다. `ip.jsp`를 로그인 API 또는 IP 조회 API라고 확정하지 않는다.

후속 세션 32는 `/servlet/Jbori` POST이며 `connection`, `count`, `command`, `sql0`~`sql4` 필드를 가진다. OTHERS 명령과 SQL 5개 중 4개가 정제된 것을 확인했다. 응답은 base64로 전달된 multipart/mixed다. 요청 Cookie 헤더가 있다는 사실만으로 세션 29의 쿠키 재사용이나 인증 완료를 입증할 수 없다. OTHERS 배치는 읽기 전용으로 간주하거나 재전송하지 않는다.

세션 32 응답의 열 이름만 확인하려는 후속 디코딩 작업은 자동 승인 검토에서 거부됐다. 출력 축소와 별개로 입력 페이로드에 P261793 외 식별 가능한 개인정보·연락처가 포함될 수 있어 기존 사건 조회 범위 밖이라는 이유다. 해당 분석은 실행되지 않았으며 다른 도구로 우회하지 않았다. 기존 인증 관련 캡처에 포함될 수 있는 다른 사건/사용자 개인정보의 작업 전달·분석에 대한 추가 승인이 필요하다. 원문 페이로드를 프로젝트 파일로 저장하지 않았다.

이번 조사에서 새 EasyPAT 서버 요청·로그인 시도·자격 증명 읽기·정보 수정은 수행하지 않았다. 인증 어댑터와 활성 조회 정책은 계속 비활성 상태다.

### 세션 32 응답 분석 승인 후 스키마 검증 완료

사용자가 세션 32 응답의 P261793 외 개인정보·연락처 가능성을 포함한 분석을 승인한 뒤, 메모리에 있는 기존 응답을 디코딩했다. 값 대신 메타데이터만 확인했다. 5개 resultset의 열 수는 순서대로 22·44·7·1·1이며 열 이름을 근거로 회사 설정·사용자 정보·권한·서버 날짜·시간으로 추정한다. 이 역할 추정은 인증 성공이나 서버 권한 검증을 증명하지 않는다.

두 번째 응답에 `pw`(binary)와 `mobile_refresh_token`(char) 열이 있다. 행 값은 출력·파일 저장하지 않았고, 해당 열만으로 평문 비밀번호·해시·암호화 방식 또는 토큰 유효성을 판정하지 않았다. 기록은 `authentication-response-schema.json`에 값 없이 저장했다.

[RFC 2046 §5.1.1](https://www.rfc-editor.org/rfc/rfc2046.html#section-5.1.1)의 구분자는 선언 boundary 앞에 두 하이픈을 붙인다. 이번 MCP 응답에서는 본문 구분자가 선언 boundary 자체와 같았다. 서버 원본과 도구 변환 중 어느 쪽의 특성인지는 아직 확정하지 않는다. 검사기의 `observed-jbori` 모드는 이 관찰 형식을 명시적으로 선택할 때만 허용하며 기본 표준 모드가 자동으로 관대한 형식으로 전환되지는 않는다.

`src/protocol/response-schema.mjs`는 크기·파트 수·헤더·구분자·4개 메타데이터 행을 검사하고 열 이름·타입만 반환한다. 행의 타당성이나 로그인 성공은 검증하지 않는다. 실제 세션 32에 적용해 5개 스키마 분리를 확인했다. `fixed-read-client.mjs`에는 알려진 비밀번호·토큰 계열 열이 있으면 업무 결과 반환을 거부하는 방어를 추가했다. 합성 비밀값 비출력, 구분자 모드 분리, 잘못된 메타데이터·헤더·파트 수 거부 및 업무 결과 차단 테스트를 포함해 90개가 통과했다.

추가 승인으로 세션 32 응답 분석 차단은 해소됐다. 남은 것은 MCP가 가린 요청 SQL 4개의 인증 조건·자격 증명 변환, 세션 29 쿠키의 이름·범위, 성공/실패 및 갱신 규격이다. 이를 추측해 로그인하거나 사용자 응답의 `pw` 값을 재사용하지 않는다. 새 서버 요청과 실제 자격 증명 접근은 여전히 0건이다.

### 로그인 조건 원문 로컬 검사 및 쿠키 구조 확인

computer-use 스킬의 창 선택·관찰 후 단일 조작 절차로 기존 Fiddler 세션 32의 Form-Data `sql1`을 선택해 Copy Value로 복사했다. 화면 조작은 개발용 기존 캡처 확인에만 사용했다. `scripts/Inspect-AuthenticationClipboard.ps1`은 로컬 표준입력으로 `inspect-auth-shape.mjs`에 전달한다. 검사기는 문자열·숫자·16진수 리터럴을 `<value>`로 바꾸고 주석을 제거한다. 원문 파일·원문 지문·인증 값은 출력하거나 저장하지 않는다. 검사를 마친 현재 클립보드 값이 동일한 경우에만 완료 안내문으로 교체했다. Windows 클립보드 기록·동기화 삭제는 보장하지 않는다.

실제 SQL1은 `opms_login_member`와 `opms_login_macads`를 조회한다. 사용자 비교 조건 `userid`, `T1.id`와 비밀번호 비교 `T1.pw = dbo.EncryptTxt(...)`를 확인했다. `del_flag`, `d_retire IS NULL`, `ck_off`, `div_use` 조건도 있다. 리터럴 7개는 모두 숨긴 형태로 `authentication-request-shape.json`에 기록했다. 이 관찰은 서버 함수 호출을 증명할 뿐 암호화 알고리즘의 구현·보안성, 실제 입력 변환 또는 상수 값을 확정하지 않는다. `T1.*`로 조회되는 자격 증명 열을 향후 LLM 업무 응답으로 반환해서는 안 된다.

쿠키 값의 화면 노출을 피하기 위해 사용자에게 세션 29 응답 헤더의 로컬 복사를 요청했다. 사용자는 Set-Cookie 헤더를 채팅으로 제공했다. 프로젝트에는 값 없이 `JSESSIONID`, Path=/, Secure, HttpOnly 속성만 기록했다. Domain·SameSite·Expires·Max-Age 속성은 제공된 헤더에 없다. 원래 세션 29에서 복사됐는지는 사용자 제공 근거에 의존하며, 쿠키가 인증된 세션인지 또는 세션 32 요청과 동일한지는 검증하지 않았다. 제공된 쿠키 값은 새 요청에 사용하지 않는다.

관련 테스트 95개가 통과했다. 자동 로그인·배치 재전송·계정 자격 증명 읽기·서버 수정은 하지 않았다. 다음은 고정 배치와 입력 위치의 안전한 바인딩, 인증 성공/실패 판정 및 세션 연속성·갱신 규격 검증이다. 현재의 구조 관찰만으로 운영 인증 어댑터를 활성화하지 않는다.

### 실제 SQL1 입력 위치 바인딩 오프라인 검증

`authentication-binding.mjs`는 관찰된 SQL1의 구조 하나만 허용한다. 리터럴 7개 중 사용자 ID 2곳과 비밀번호 1곳의 위치를 고정하고, TOP 및 계정 상태 조건의 리터럴 4개는 캡처 그대로 보존한다. 사용자 ID 두 위치의 실제 캡처 값이 같은지 확인한다. 다른 함수·조건·추가 문장·주석·지원하지 않는 리터럴 형식은 거부한다. 일반 SQL 치환 도구가 아니다.

[Microsoft SQL Server 문자열 상수 문서](https://learn.microsoft.com/en-us/sql/t-sql/data-types/constants-transact-sql?view=sql-server-ver17)의 단일 따옴표 처리 규칙을 적용하고, 치환 후 다시 분석해 입력값 왕복 일치·고정값 보존·구조 불변을 검사한다. 서버 prepared statement를 사용하는 방식은 아니다. 문자 인코딩·콜레이션이 미확정인 비ASCII 자격 증명과 제어문자는 현재 거부한다. 기존 N 접두사는 보존한다.

computer-use 스킬을 사용해 기존 세션 32의 SQL1만 다시 Copy Value로 로컬 복사했다. `Inspect-AuthenticationClipboard.ps1 -Mode binding -ClearCopiedValue`는 원문을 비공개 표준입력으로 전달하고 합성 사용자명/비밀번호로 치환 검사를 실행했다. 실제 캡처에서 구조 일치, 사용자 ID 두 위치의 동일성, 입력 위치 3개 교체, 고정값 4개 보존 및 왕복 검증이 성공했다. 원문·원래 자격 증명·치환된 SQL은 파일이나 출력에 남기지 않았다. 컴파일 결과는 해당 프로세스 메모리에서만 사용했으며 운영 템플릿으로 저장하지 않았다.

`assessLoginIdentity`는 신뢰된 내부 투영기가 제공한 ID 값 목록과 스키마 확인 여부를 받아 일치·불일치·없음·중복·미검증 상태를 구분한다. ID나 자격 증명 값을 반환하지 않으며 모든 경우에 인증 확인/세션 발급은 false다. 이 모듈은 실제 resultset 투영기나 로그인 성공 판정기가 아니고, 서버의 실패 응답을 관찰하지 않은 상태에서 결과 없음에 '비밀번호 오류'라는 의미를 부여하지 않는다.

테스트 102개가 통과했다. 실제 SQL1 오프라인 바인딩 증거는 `authentication-binding-status.json`에 기록했다. 나머지 인증 배치, 비밀정보 없는 운영 템플릿 준비, 응답과 쿠키의 연속성, 실제 성공/실패 판정 및 갱신은 후속 검증 대상이다. 이번 단계에서도 새 서버 요청·자동 로그인·Windows 자격 증명 읽기·서버 수정은 0건이다.

### 전체 인증 배치와 쿠키 연속성 검증

computer-use 스킬로 기존 세션 32의 Form-Data 전체 복사 기능을 사용했다. 복사 결과는 URL 인코딩 본문이 아니라 `Key=필드; Value=값`의 8개 행이었다. 처음 검사기는 이 형식을 거부했으며, 값은 출력하지 않고 구분자만 확인한 뒤 관찰된 형식만 추가했다. `authentication-batch.mjs`는 중복·누락 필드, 잘못된 count/command, 정제된 원문, 변경 요청을 거부한다. 이는 오프라인 구조 검사이며 SELECT 형태 자체로 배치 재전송을 허용하지 않는다.

SQL0은 회사 설정 `opms_code_setting`, SQL1은 계정·단말 정보, SQL2는 `opms_login_member_right` 권한, SQL3·4는 서버 날짜·시간을 조회한다. SQL2의 마지막 ID 조건은 SQL1의 사용자 ID와 로컬 값 비교에서 일치했다. `authentication-batch-binding.mjs`는 관찰된 다섯 구조와 순서를 고정하고 ID 3곳·비밀번호 1곳만 함께 치환한다. 나머지 리터럴 23개와 날짜/설정 쿼리를 보존한다. 실제 전체 캡처에 합성 입력을 적용한 로컬 검사가 통과했으며 원래 자격 증명이 없는 메모리 내 템플릿만 컴파일했다. 실행용 파일로 저장하지 않았다.

쿠키 비교에는 세션 29의 응답 Headers Copy와 세션 32의 요청 Headers Copy를 사용했다. Headers 복사 형식은 Form-Data와 달리 `Key: 필드; Value: 값`이었다. `Compare-AuthenticationCookies.ps1`은 첫 헤더를 메모리에 보관하고 최대 60초 동안 두 번째 복사를 기다린 후 대소문자 구분 정확 비교로 JSESSIONID 값이 같음을 확인했다. 출력은 이름·일치 여부뿐이며 쿠키 값이나 해시는 기록하지 않았다. 비교 후 현재 클립보드가 검사한 값과 같을 때만 완료 안내문으로 교체했고 프로세스가 종료됐다. 클립보드 기록·동기화까지 삭제한 것은 아니다.

이것은 캡처 29→32의 쿠키 전달 증거이며 인증 성공·권한 강제·쿠키 만료·세션 갱신 증거가 아니다. 기록은 `authentication-batch-status.json`과 `authentication-cookie-continuity.json`에 있다. 테스트 109개 및 실제 로컬 배치/쿠키 비교가 통과했다. 남은 것은 비밀정보 없는 운영용 템플릿 준비, 응답의 ID·권한 투영 검증, 통제된 인증 어댑터와 실제 성공/실패·갱신 검증이다. 새 서버 요청·자격 증명 읽기·서버 수정은 이번에도 0건이다.

### 캡처 성공 교환 판정과 후보 인증 어댑터

기존 세션 32의 전체 요청과 응답을 같은 로컬 프로세스 메모리에서 대조했다. 응답의 5개 resultset은 관찰된 열 이름·타입·길이·플래그와 정확히 일치했고 행 수는 1·1·8·1·1이었다. 두 번째 결과의 사용자 ID는 요청에 결합된 ID와 일치했고, 세 번째 결과의 권한값은 SQL2의 각 `CASE`가 사용하는 참·거짓 리터럴 규칙에 맞았다. 세션 29 응답과 세션 32 요청의 JSESSIONID 연속성도 함께 요구했다. 비밀번호·토큰·연락처·쿠키 값은 출력하거나 파일에 저장하지 않았다. 이 근거는 `authentication-exchange-status.json`에 기록했다.

이 조합을 `captured-successful-session-exchange-observed`로 분류한다. 이는 이미 로그인되어 성공한 기존 캡처의 요청·응답 관계를 판정한 것이며, 현재 자격 증명을 사용한 새 로그인 성공이나 실패 응답의 의미를 검증한 것은 아니다.

실제 캡처의 계정 값을 안전 표식으로 치환해 자격 증명이 없는 5문장 인증 템플릿을 만들었다. 고정 지문을 `authentication-template.json`에 등록하고 `.local/authentication`에 Windows 현재 사용자 범위 DPAPI 암호문으로 저장한 뒤 복호화·지문·입력 위치 3+1개의 왕복을 확인했다. 평문 인증 템플릿과 계정 값은 저장하지 않았다.

`authentication-transport.mjs`는 두 HTTPS URL, POST, TLS 1.2 이상, 인증서 검증, 응답 크기·형식과 무리다이렉트·무재시도를 고정한다. `authentication-adapter.mjs`는 DPAPI 템플릿 로드, 자격 증명 결합, JSESSIONID 선택, 15분 이하 로컬 임대, 5개 응답 투영과 ID·권한 판정을 하나의 후보 흐름으로 연결했다. 현재 어댑터는 의도적으로 `verified:false`이고 `authenticate`를 제공하지 않아 세션 공급기나 업무 조회 런타임에서 사용할 수 없다.

모의 전송 및 합성 응답을 포함한 전체 테스트 121개가 통과했다. 이번 단계의 새 서버 요청, Windows 자격 증명 읽기, 실제 로그인, 서버 수정은 모두 0건이다. 다음은 전용 자격 증명 항목을 값 노출 없이 확인하고, 정책상 최대 한 번의 통제된 실제 성공 로그인으로 같은 판정을 재검증하는 것이다. 실패 응답과 세션 갱신은 별도의 관찰 전까지 계속 비활성이다.

이후 `CredentialStatus` 작업을 추가해 전용 항목의 존재와 필수 필드 유무만 확인했다. 자격 증명 blob은 복사·디코딩하지 않으며 출력은 불리언 상태뿐이다. 실제 확인 결과 `EasyPAT/Automation` 항목은 없었다. 서버 요청이나 로그인은 보내지 않았다. `Register-EasyPatCredential.ps1`은 사용자가 로컬 터미널에서 사용자명과 비밀번호를 직접 입력하는 보안 프롬프트를 제공하고, 비밀번호를 명령행·파일·출력에 남기지 않으며 기존 항목을 덮어쓰지 않는다. 스크립트 안전 규칙을 포함한 전체 테스트 123개가 통과했다.

### 대화형 사용자 저장소 이관과 최초 자동 로그인 검증

Codex 샌드박스 계정에서 만든 DPAPI 암호문은 실제 Windows 사용자 계정에서 복호화할 수 없으므로, RSA-OAEP-SHA256과 AES-256-GCM을 결합한 일회성 전달 파일로 인증 템플릿과 읽기 템플릿 2건을 이관했다. 개인키는 대상 사용자 DPAPI로 보호했고 이관 후 평문·전달 파일·개인키를 삭제했다. 대상 저장소는 `.local/authentication-user`와 `.local/templates-user`이며 Git에서 제외된다. 대상 계정에서 복호화와 등록 지문 일치를 확인했다.

사용자가 Windows 자격 증명 관리자에 `EasyPAT/Automation`을 등록한 뒤, 최초 로그인 성공 경로를 실제 서버에서 한 번 검증했다. 빈 본문의 `ip.jsp` POST와 고정 OTHERS 5문장 POST만 전송했고, 투영된 사용자 ID 일치, 권한 8행, JSESSIONID 수신을 확인했다. 쿠키는 프로세스 밖으로 반환하거나 저장하지 않았고 자동 재시도·업무 조회·서버 수정은 없었다. 이 근거로 최초 로그인 어댑터를 런타임에 연결했지만 실패 응답과 갱신은 계속 비활성이다.

### P261793 본문 후보 바인딩 기각

`matter-detail.main-record.v1` 후보로 P261793 고정 조회를 한 번 시도했으나 실패 후 자동 재시도 없이 종료했다. 당시 Fiddler 캡처가 꺼져 있어 실패가 로그인·전송·응답 검증 중 어디에서 발생했는지와 실제 요청 수는 확정하지 못한다. 응답 행은 저장하지 않았다.

후속 오프라인 검사에서 후보의 원본 캡처 세션 168 응답을 다시 판독했다. HTTP 200 `text/resultset`이며 메타데이터 4행과 데이터 1행, 205열로 구조화되었지만 값 181개가 Fiddler에 의해 정제되어 있었다. 열 이름은 정제되지 않았고 `ourref` 열도 존재했으나 그 값은 P261793과 정확·공백정리·대소문자 무시 비교에서 모두 일치하지 않았다. 마스킹되지 않은 다른 셀에도 P261793은 없었지만, 마스킹된 셀의 원래 값은 판정할 수 없다. 실제 값은 출력하거나 저장하지 않았다.

이는 세션 168이 다른 사건임을 증명하지 않는다. 기존 로컬 클립보드 검사에는 P261793 검색 세션 119의 `idx`와 세션 168 SELECT의 `idx` 조건이 같다는 근거가 있다. 다만 현재 업무 클라이언트는 응답 `ourref=P261793`을 요구하므로 이 응답을 거부하며, MCP에서는 검색·본문 양쪽 `idx`가 모두 마스킹되어 응답 내부키까지 독립적으로 재대조할 수 없다. 운영 레지스트리에서 해당 지문과 사건 바인딩을 제거하고 모든 업무 조회 템플릿을 비활성화했다. 다음 실제 조회 전에 검색 결과 `idx`→고정 SELECT `idx` 조건→응답 한 행 `idx`의 연쇄를 값 비노출 방식으로 검증해야 한다. UI 상세 진입은 이미 UPDATE 2건이 관찰되어 재생하지 않는다.

`response-identity.mjs`는 지문이 고정된 SELECT에서 정확히 한 개의 `idx` 리터럴 조건만 메모리로 추출하고, 응답 한 행의 `idx`와 같은지 확인한다. 내부키를 결과·오류·파일에 포함하지 않는다. 실제 DPAPI 템플릿과 기존 P261793 검색 연결 근거를 사용한 오프라인 사전검사는 통과했으며 운영 레지스트리는 계속 비활성이다.

별도 1회용 게이트로 자동 로그인 2건과 고정 SELECT 1건을 전송한 두 번째 실제 검증은 응답을 받은 뒤 `RESULTSET_REJECTED`로 종료됐다. 단계 코드상 인증·전송은 완료됐고 자동 재시도와 수정 요청은 없었다. 세션 168 메타데이터를 값 없이 진단한 결과 업무 결과 파서가 한글 열 이름 5개와 `timestamp` 타입을 허용하지 않은 것이 원인이었다. Unicode 문자·숫자·밑줄로 된 128자 이하 열 이름과 이미 인증 파서에서 지원하는 관찰 타입만 추가하고, 공백·점·제어문자·이모지는 계속 거부하도록 회귀 테스트를 추가했다.

파서 수정 후 새로운 1회용 게이트에서 자동 로그인 2건과 같은 고정 SELECT 1건을 다시 검증했다. 응답은 1행·205열이었고 고정 문장의 유일한 `idx` 조건과 응답 한 행의 `idx`가 정확히 일치했다. 비어 있지 않은 필드는 29개였지만 행 값·내부키·쿠키는 출력하거나 저장하지 않았다. 자동 재시도와 서버 수정은 없었다. 성공 근거는 `p261793-live-main-identity-v3.json`에 기록했다.

검토 후 운영 레지스트리에는 정확한 지문 `matter-detail.main-record.v1`과 전체 당소관리번호 P261793 조합 하나만 활성화했다. 안전 정책도 같은 템플릿·사건 조합만 허용하며, 고정 문장의 `idx` 조건과 응답 `idx`가 일치하지 않으면 전체 응답을 거부한다. UI 상세 진입, 다른 사건, 진행사항·문서·다운로드 및 모든 쓰기 요청은 계속 비활성이다. 전체 139개 테스트가 통과했다.

### P261793 진행기록 직접 조회와 안전 투영

세션 174의 복사된 단일 SELECT는 읽기 전용 검사와 SHA-256 지문화에 통과했다. 원문은 Windows 현재 사용자 범위 DPAPI 저장소에만 보관했다. 같은 프로세스 메모리에서 본문 템플릿의 고정 `idx`와 진행기록 템플릿의 유일한 `idx_parent` 조건이 정확히 한 번 일치함을 확인했으며 값은 출력하거나 기록하지 않았다.

별도 1회용 게이트로 자동 로그인 2건과 고정 SELECT 1건을 전송했다. 응답은 2행·55열이었고 열 이름과 순서가 캡처 스키마에 정확히 일치했으며 모든 행의 `idx_parent`가 고정 조건과 일치했다. 자동 재시도·서버 수정·원문 행 또는 내부키 저장은 없었다. 이 근거로 `matter-detail.progress-records.v1`과 전체 당소관리번호 P261793 조합만 운영 허용 목록에 추가했다.

### P261793 문서 목록, 고정 파일 다운로드와 로컬 OCR

세션 247의 문서 목록 SELECT를 DPAPI 저장소에 보관하고 27열 전체 스키마 및 `DELETEFLG`, `DOC_NUM`, `DIV`, `GRP_KEY` 네 고정 조건이 응답 7행 모두와 일치함을 실제 서버에서 검증했다. 문서 파일명은 P261545를 대표로 하는 공유 그룹이어서 P261793 문자열을 포함하지 않는다. 따라서 일반 사건 연결 규칙으로 확장하지 않고, 사용자가 확인한 P261793 화면 문맥과 세션 245→247→249의 고정 캡처 흐름에만 결합했다. 운영 목록 결과에는 서버 업로드 경로와 내부키를 반환하지 않는다.

세션 249에서 관찰된 문서 목록 2번 JPEG만 별도 허용 목록에 추가했다. 자동 로그인 후 문서 목록을 새로 검증하고 같은 메모리 내 JSESSIONID로 고정 원본 호스트의 파일 GET을 한 번 수행했다. 응답은 `image/jpeg`, 51,373바이트였고 저장 파일 SHA-256은 `74fe072fb2ac8e0ac0e989370a82ef7770f00eccaffa4a9df2f43cf47817c778`이다. TLS 검증, 64MiB 상한, 리다이렉트·재시도 금지, 정확한 Content-Length 및 기존 파일 비덮어쓰기를 적용했다. 서버 업로드 경로와 쿠키는 출력하거나 저장하지 않았다.

다운로드한 이미지는 외부 서비스로 보내지 않고 Windows Media OCR로 처리했다. 작은 글자 인식을 위해 ffmpeg로 4배 확대·흑백·대비·샤프닝 사본을 만든 뒤 한글 OCR을 실행했다. 금액 표현 `600+60`, `550-220`, `550-110`, `100+10` 및 특허·변리사·직무·성과·연구전담부서 키워드를 구조화했다. 이미지 본문 자체에는 P261793이 없으므로 OCR 결과로 사건번호를 추론하지 않는다. 원문 OCR과 전처리 파일은 Git 제외 `.local` 아래에만 있다.

### 로컬 EasyPAT MCP 서버

`@modelcontextprotocol/sdk`의 `StdioServerTransport`로 네트워크 포트를 열지 않는 로컬 MCP 서버를 구현했다. 사건 요약 도구는 검증된 전체 당소관리번호 문법만 받고, 진행기록·문서·다운로드·OCR은 P261793과 허용된 다운로드 위치 2번·고정 파일명의 리터럴 스키마를 유지한다. SQL·쿠키·URL·내부키·서버 업로드 경로를 받거나 반환하는 도구는 없다. 런타임 오류는 원문을 제외한 `EASYPAT_OPERATION_FAILED`로 축소한다.

인메모리 MCP 협상과 실제 자식 `stdio` 프로세스 통합 테스트를 통과했다. 이후 실제 Windows 사용자 문맥에서 MCP 서버를 띄워 6개 도구 목록, 자동 로그인, P261793 문서 목록 7건 및 기존 로컬 OCR의 금액 표현 4개·키워드 5개를 검증했다. 문서 항목 원문, OCR 원문, 쿠키와 SQL은 출력하지 않았고 서버 수정과 자동 재시도는 없었다.

Codex 사용자 설정에 `easypat` 이름으로 활성 등록했으며 Node.js와 서버 엔트리 모두 절대 경로를 사용한다. 실행 중인 작업은 새 MCP 도구를 동적으로 불러오지 못하므로 새 Codex 작업에서 도구가 나타난다. 개발용 Fiddler 캡처는 마지막 확인 시 아직 켜져 있으므로 UI에서 캡처를 끈 뒤 임시 연결과 키를 폐기해야 한다. 운영 EasyPAT MCP 서버는 Fiddler에 의존하지 않는다.

전체 회귀 테스트가 통과했다. 운영 정책은 범용 사건 요약의 검증된 검색→내부키→본문 SELECT 연쇄와 P261793의 세 고정 SELECT 및 목록 2번 JPEG 하나만 허용한다. 다른 사건의 진행기록·문서·파일, 세션 자동 갱신과 모든 서버 수정은 계속 차단한다.

### 사건번호 일반화 1단계: 오프라인 바인딩 경계

P261793 고정 경로를 복제하는 대신, 범용 조회가 반드시 거쳐야 하는 경계를 코드로 먼저 고정했다. 새 사건번호 파서는 `T`, `PT`, `PPT`, `P` 계열만 허용하고 전체 문자열을 대문자로 정규화하되 접미사를 삭제하지 않는다. `-CN`과 `-CN(PA)`, `-S1`과 `-S2`는 서로 다른 사건으로 유지하며 접미사만으로 그룹 관계를 만들지 않는다.

기존 세션 117과 119를 다시 확인해 검색이 건수 조회와 결과 행 조회 두 SELECT로 구성되고, 각각 국내·해외·이심·기타 네 테이블의 `ourref LIKE '%P261793%'` 리터럴을 반복함을 확인했다. 검색 바인더는 지문이 정확히 일치하는 각 SELECT에서 네 LIKE 리터럴이 모두 같은 기준 사건번호인지 확인한 뒤 네 곳을 함께 치환한다. 본문 바인더는 등록된 내부 키 `열 = 문자열 리터럴` 한 곳만 치환한다. 주석, 누락·추가 후보, 구조 변화, 마스킹 값, 변경된 지문을 거부하고 치환 후 토큰 구조가 동일한지 다시 확인한다. 호출자는 SQL·URL·쿠키·내부 키·재시도 옵션을 전달할 수 없다.

건수 응답 `recCount`가 문자열 `1`인 경우에만 결과 행 조회를 수행하고, 결과는 전체 당소관리번호가 정확히 일치하는 1행만 허용한다. 검색 결과의 내부 키는 공개 객체에 넣지 않고 프로세스의 `WeakMap`에만 보관하며, 위조한 객체로 본문 템플릿을 바인딩할 수 없다. 본문 응답도 바인딩된 내부 키와 일치해야 하며 외부 결과에는 7개 업무 필드만 투영한다. 실패 시 자동 재시도하지 않는다.

세션 117·119 요청 원문은 터미널 반향을 끈 입력 채널로 검사 프로세스에 전달했다. 두 템플릿은 Windows 현재 사용자 DPAPI 저장소에만 암호화 보관했고 복호화 지문 왕복을 확인했다. 프로젝트에는 원문 대신 SHA-256 지문, 네 개 LIKE 슬롯, 응답 열 이름만 기록했다. 이 과정의 새 서버 요청은 0건이다.

첫 기준 검증은 네트워크 전에 본문 205열 순서가 레지스트리에 고정되지 않은 것을 발견해 사전검사에서 종료됐다. 기존 세션 168 응답에서 행 값은 저장하지 않고 열 이름 205개만 추출해 `main-record-response-schema.json`에 고정했다. 이 시도에서 로그인·검색·본문 서버 요청은 발생하지 않았고 일회성 실행 게이트도 점유하지 않았다.

스키마 고정 후 실행한 v1 기준 검증도 서버 요청 전에 종료됐다. 명령 실행 계정은 `codexsandboxoffline`으로, 실제 Windows 사용자 DPAPI의 기존 본문 템플릿과 자격 증명을 읽을 수 없었다. 검색 템플릿은 반대로 샌드박스 DPAPI에 저장돼 실제 사용자 런타임에서 사용할 수 없다. v1 실패 게이트는 진단 기록으로 보존한다. v2 검증기는 자격 증명과 인증·검색·본문 템플릿이 모두 현재 사용자로 복호화되는지 확인하기 전에는 일회성 게이트를 만들지 않도록 수정했다.

검색 템플릿 전용 handoff 내보내기/가져오기 명령을 추가했다. 실제 사용자가 일회성 RSA 개인키를 DPAPI로 보호해 생성하면 샌드박스는 공개키로 두 검색 템플릿을 AES-256-GCM 암호화하고, 실제 사용자는 이를 복호화해 자신의 DPAPI 저장소에 넣는다. 성공 시 공개키·개인키·전달 번들을 삭제한다.

실제 사용자 DPAPI 이관 후 로컬 사전검사에서 자격 증명, 인증 템플릿, 검색 템플릿 2건, 본문 템플릿과 숫자/문자 내부키 바인딩이 모두 준비됐음을 확인했다. 이어 v2 일회성 게이트로 P261793 범용 기준 경로를 실제 검증했다. 건수 응답은 정확히 1, 검색 결과는 정확히 1행이며 전체 `ourref`가 일치했고, 검색 응답의 `idx`로 바인딩한 본문 응답도 같은 내부키와 205열 스키마를 만족했다. 외부에는 7개 업무 필드만 투영했다. 업무 SELECT는 건수·결과·본문 각 1건으로 총 3건이며 자동 재시도와 서버 수정은 없었다.

이 성공은 템플릿 구조와 P261793 기준 경로를 검증한 것이지 임의 사건의 안전성을 확정한 것은 아니다. 범용 운영 및 MCP 입력 확장은 사용자가 조회 권한을 확인한 서로 다른 비기준 사건 최소 2건에서 동일한 건수·정확 사건번호·내부키·본문 스키마 연쇄가 성공한 뒤에만 검토한다. 실제 사용자 이관과 기준 검증 후 샌드박스 DPAPI 백업 2개를 삭제했고, 실제 사용자 암호화 사본은 유지된다.

첫 비기준 사건 PT261129와 두 번째 비기준 사건 PT261130의 일회성 실제 검증이 모두 성공했다. 각 사건에서 건수 1건, 검색 결과 1행, 전체 사건번호, 검색 내부키와 본문 응답 내부키, 205열 스키마를 확인했으며 7개 안전 필드만 투영했다. 각 업무 SELECT는 3건이었고 자동 재시도·서버 수정·원본 행·내부키 반환은 없었다.

두 비기준 사건 검증 완료 후 `generic-read-template-registry.json`의 사건 요약 연쇄만 운영 후보로 활성화했다. MCP의 기존 `easypat_get_matter_summary` 입력을 전체 당소관리번호 문법으로 넓혔지만 도구 수는 6개로 유지했다. 새 운영 어댑터는 검증 완료 수와 승인 목록, 세 템플릿 지문, 읽기 전용 정책, TLS, 정확한 검색 건수·사건번호·내부키·205열 스키마를 모두 확인해야 생성된다. 진행기록·문서·다운로드는 범용화하지 않았으며 문서 그룹 키도 별도 의미 검증 대상으로 남는다.

첫 범용 MCP 실제 검증은 `mcp-generic-summary` 단계에서 약 0.34초 만에 실패했다. 원문 값·내부키는 반환되지 않았고 자동 재시도와 서버 수정도 없었다. 실제 HTTPS 3단계 조회보다 짧은 시간에 종료된 점을 근거로 로컬 자격증명·DPAPI 템플릿·바인딩 또는 런타임 경계를 먼저 진단한다. 진단 중 반복 호출을 막기 위해 `mcpExposureEnabled`를 false로 바꾸고, 서버 요청 수가 0인 실제 사용자 사전검사를 다음 단계로 지정했다.

### 사건번호 일반화 2단계: 진행기록·문서·다운로드

범용화 범위를 사건 요약에 한정하지 않고 진행기록·문서 목록·선택 파일 다운로드까지 확장한다. 진행기록은 이미 P261793에서 본문 `idx`와 진행기록 SELECT의 유일한 `idx_parent` 조건, 그리고 모든 응답 행의 `idx_parent`가 일치함을 검증했다. 이 구조를 정확한 사건 검색이 반환한 내부키에 연결하는 범용 후보를 구현했다. 호출자는 전체 당소관리번호만 전달할 수 있고, SQL·내부키·재시도 옵션은 전달할 수 없다. 출력은 기존 13개 업무 필드로 제한한다. 운영과 MCP 노출은 PT261129·PT261130 실제 검증 전까지 비활성이다.

문서 목록의 최초 후보는 정확한 사건 검색 결과의 내부 `idx`를 문서 SELECT의 `GRP_KEY`에 바인딩하도록 설계했다. 그러나 실제 사용자 DPAPI 문맥에서 두 기준 템플릿을 값 비노출·서버 요청 0건으로 비교한 결과 두 값이 다름을 확인했다. 이 직접 연결 후보는 레지스트리에서 제거했다. P261793 문서 파일명에도 사건번호가 없으므로 파일명으로 연결을 추정하지 않는다. 다음은 기존 본문·진행기록·관련건수 템플릿의 고정 조건과 문서 그룹키를 값 비노출로 비교하고, 연결이 없으면 위임계약서 탭에서 문서 목록 직전의 읽기 전용 세션 245를 중간 그룹키 출처 후보로 검사하는 것이다.

다운로드 일반화의 오프라인 후보도 구현했다. 입력은 전체 당소관리번호·목록 위치·예상 파일명으로 제한하고, 매번 검색과 문서 목록을 새로 검증한 뒤 서버 업로드 경로를 직렬화되지 않는 일회성 내부 문맥으로만 다운로더에 전달한다. 같은 EasyPAT 출처의 64MiB 이하 지원 형식만 사건별 새 폴더에 저장하고 SHA-256을 계산한다. 업로드 경로 직접 입력, 기존 파일 덮어쓰기, 리다이렉트, TLS 무시, 자동 재시도와 서버 수정은 금지한다. 활성화 순서는 문서 목록 실제 교차검증 다음이다.
